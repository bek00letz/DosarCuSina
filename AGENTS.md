# AGENTS.md — Dosar cu Șină

Instructions for AI coding agents and the people who run them. Read this whole file before you change anything. The repository is **public**.

Read next, in this order: [docs/DECISIONS.md](docs/DECISIONS.md), [docs/HANDOFF.md](docs/HANDOFF.md), [SPEC.md](SPEC.md), [CONTRIBUTING.md](CONTRIBUTING.md) and [docs/COPY_GUIDE.md](docs/COPY_GUIDE.md).

# The standing rule

**Everything we make together — apps, sites, scripts with UI, artifacts, dashboards, even CLI output — has to look and feel like something Apple shipped.**

This is not about a visual style (not "make it white", not "add Liquid Glass"). It's about the small details people never notice consciously but always feel. Before calling anything done, check it against this list:

## Feel
- Motion uses springs, not linear or default ease curves. Short (≈0.2–0.4s), interruptible, and it respects Reduce Motion.
- Every interaction answers back right away: press states, hover states, focus rings, haptics where the platform has them.
- Nothing jumps. Layout shifts, content popping in, and spinners that flash for 50ms are bugs. Use skeletons or fade-ins, and hold back loading indicators until a delay has passed.
- Sensible defaults so the first run already feels right. Fewer settings, not more.

## Look
- Typography does the hierarchy: the system font stack (SF Pro / -apple-system), tight tracking on large titles, a real type scale, tabular numbers where digits line up.
- Spacing sits on a consistent grid (4/8pt). Optical alignment wins over mathematical alignment when they disagree.
- Concentric corner radii (inner radius = outer radius − padding), continuous/squircle corners where possible.
- Restrained color: one accent, semantic colors, real dark mode (not inverted), hairline separators instead of heavy borders.
- Icons are SF Symbols, or match their weight and optical size.

## Care
- Empty states, error states, and edge cases get designed too, not left as defaults. Error messages are human, specific, and say what to do next.
- Copy is short and plain, in sentence case. No jargon, no exclamation marks.
- Accessibility is built in: Dynamic Type / scalable text, contrast, VoiceOver labels, keyboard navigation, hit targets of 44pt or more.
- Works at every size: phone width, narrow windows, huge screens. No horizontal scroll, no clipped text.
- Small touches nobody asked for: a correct app/tab icon, a sensible window title, remembered state, natural keyboard shortcuts, smart truncation.

When a tradeoff comes up between shipping fast and getting these details right, flag it instead of quietly dropping the detail.

# Framework, not patch

**Framework, not patch.** Fix the cause, not the symptom: a change that only makes one scenario look right isn't done, and say plainly when something is only a mitigation. Build for every case of its kind (every device, size, user and source), not the one on my desk: no hard-coded models, sizes, addresses or names. One source of truth, never a second path that does the same thing slightly differently. Pin the behaviour with tests. When a decision comes up, give the right long-term design, not the easy one.

# How agents work here

1. **Read first.** [docs/DECISIONS.md](docs/DECISIONS.md) says what was decided and why; [docs/HANDOFF.md](docs/HANDOFF.md) says where work stands and what the last session left. Don't undo a decision quietly: if you think one is wrong, say so in the pull request or an issue.
2. **One branch per task**, named `<person>/<topic>`, for example `ana/visit-wording`. Branch from an up-to-date `main`.
3. **Never push to `main`.** Open a pull request into `main` using the template. The owner reviews every one.
4. **Conventional commits** (see section 7), each one building on its own.
5. **Test lightly while working, fully once.** Run only the suites that cover your change while you iterate; after a fix, rerun only what failed. Run the whole suite (`./tests/run_tests.sh`) once before opening the pull request, and say in it which simulator you used. The pull request runs it again on GitHub (see "Checks on every pull request").
6. **Only simulators that are already installed.** Pick from `xcrun simctl list devices available`. Never download a simulator runtime or platform, and don't create devices for other OS versions. If a task truly needs one that isn't there, ask.
7. **No screenshots without asking.** Verify with builds and tests first. If only a screenshot or the simulator can show something, ask the person you work with before taking one, or ask them to look.
8. **Placeholder data only**, everywhere: code, tests, previews, fixtures, screenshots, commit messages. Plates like `B-123-ABC`, cars like `VW Golf 2018`, firms like `ENGIE Romania S.A.`, email like `nume@exemplu.ro`. A made-up CNP uses county code `99` with a valid control digit, such as `1800101990006`; the privacy check rejects any other CNP that passes the checksum. Card numbers are only the published test numbers, such as `4111 1111 1111 1111`; the privacy check rejects any other number that passes the card check digit. IBANs are the specifications' own examples, such as `RO49 AAAA 1B31 0075 9384 0000` or `GB82 WEST 1234 5698 7654 32`, or built when the test runs on the placeholder bank code `AAAA`.
9. **End each session by updating [docs/HANDOFF.md](docs/HANDOFF.md)**: append a "last session" entry and fix anything in "current state" your work changed.
10. **Ask before design choices.** When a layout or product change could reasonably go more than one way, name the options and ask. Obvious bugs with one clear fix: just fix them.
11. **Keep a way back.** When replacing something that works, keep the old version disabled (not deleted) until the new one is proven, and ask before removing it. `ios/Legacy/` and `tests/legacy/` are kept this way.
12. **Security problems are never written in the repository.** See section 5.

Turn on the hooks once per clone: `git config core.hooksPath .githooks`. Before each commit they run the privacy check and the architecture check.

- **Never add a line or raise a count without the owner's OK.** The pull request check fails on that unless the owner labels the pull request `architecture-exception`.

- A rule that seems wrong is a question for the owner: say so in the pull request. Never work around a pattern.

## The database's shape

Models live in the current `VersionedSchema` ([Models/Schema/DosarSchema.swift](ios/DosarCuSina/Models/Schema/DosarSchema.swift)); code uses the type aliases (`Asset`, `Obligation`, …) and `CurrentSchema` for the schema itself, never a version: only `Models/Schema/` (the schema, its frozen versions, the migration stages) names one (the `frozen-schema-version` check). A change to what is stored is a new version: freeze the one before it in [Models/Schema/Versions/](ios/DosarCuSina/Models/Schema/Versions/) (stored attributes and relationships only, exactly as they were), add a stage to `DosarMigrationPlan`, and pin both in `SchemaMigrationTests` (the frozen shape's fingerprint, and a store written by the version before that opens with everything in it). Keep it CloudKit-shaped: optional or defaulted, no unique constraints. A day is stored as a day, never as a `Date`: its ISO text through `StoredDay`, read and written only through the model's `CalendarDay` property (`Obligation.dueDay` and `snoozedUntil`, `HistoryEntry.cycleDueDay` and `nextDueDay`, `Attachment.documentDay` and `validUntil`); sort by it with `Obligation.byDueDay`. Only a moment (when something happened, was made or changed) is a `Date`, and `DaysStoredAsDaysTests` lists every one. A version that changes how something is stored moves it in a custom stage, and what a custom stage carries across the change of shape goes through `MigrationCarry` ([Models/Schema/MigrationCarry.swift](ios/DosarCuSina/Models/Schema/MigrationCarry.swift)), never in memory between `willMigrate` and `didMigrate`: the stage reads it before the store changes shape and keeps it in a file beside the store (`MigrationCarry.keep`, throwing when it can't, so the store stays as it was), and `PersistenceController.makeContainer` finishes every carry still there, oldest stage first, before anything reads the store (`finishPending`; the carry's `finish`, against the current models, saved once, change times untouched, the same when run twice), then removes its file. An upgrade killed halfway finishes at the next launch by that same path. A new custom stage is a new `MigrationCarrying` type listed in `MigrationCarry.carries` (`DayMigration` for the days of version 9, `LockMigration` for the locks of version 12), with a test that stops the upgrade after the shape changes and reopens. Existing data that needs fixing goes through a `DataRepairs` step, which asks first. Every model keeps when it last changed (`updatedAt`, `ChangeTimed`); a new model does too, or is part of one that does (`PartOfChangeTimed`, as a page is of its document). A new property goes into its model's `storedProperties` (`.links` for the side of a many-to-many link the record keeps itself), travels in the archive unless it belongs to this phone (`DossierV3.stayOnThePhone`), and `ArchiveMergeTests` fails until it does.

## Everything outside the database

`UnitOfWork` ([Services/Persistence/UnitOfWork.swift](ios/DosarCuSina/Services/Persistence/UnitOfWork.swift)) is how actions save. Every action saves through `UnitOfWork.save(context)`; never call `context.save()` from an action or a view. Nothing saves by itself: a container is made only by `PersistenceController.makeContainer` and a context of its own only by `PersistenceController.context(in:)` ([Services/Persistence/PersistenceController.swift](ios/DosarCuSina/Services/Persistence/PersistenceController.swift)), both with SwiftData's autosave off, so a change left on a context is written only by the next unit (the `context-outside-persistence` check). When one tap does several things (file a document under a new person, log a visit with its invoice, complete a deadline with the new document), wrap them in `UnitOfWork.perform(in:)`: the actions inside only record their changes and the unit saves once, everything or nothing. A unit never waits: it takes synchronous work only, so gather what takes time (a capture's pages, Face ID) before it opens; then no other save can slip into it or be rolled back with it. Actions never roll back on their own; an action that does several things wraps them in `perform`, which joins the caller's unit. Every question for the person (`StepQuestion`: a lower counter, something of theirs in an example) is asked before a unit writes anything: plan the step's reading (`PlannedReading`) and ask with `HouseholdMutations.askAboutReading` and `ExampleOwnership.requireReal` before the unit opens, and a flow that wraps actions asks all of their questions first (`CaptureFiler.askFirst`). Every save masks card numbers in the words of the records it writes, a backup's own writer included (`FreeText`). Work that must only happen once the changes are kept goes in `UnitOfWork.afterCommit(in:)`. Change times are kept by the unit as it saves (`ChangeTimes`, [Services/Persistence/ChangeTimes.swift](ios/DosarCuSina/Services/Persistence/ChangeTimes.swift)): in the person's step, every record whose own values or links a save changes gets a new `updatedAt`, and what a step makes gets the time it was made. `ChangeTimes` is the only writer of `updatedAt` beside the importer (the `change-time-outside-change-times` check): an action with a clock passes it to the unit (`UnitOfWork.perform(in:now:)`, `performUndoable(in:now:)`, `save(_:now:)`; a unit opened without one takes the first a step inside it gives), never writes the time itself. A step the app takes by itself opens its unit with `origin: .app` (`ChangeOrigin`: the catalog's categories, the repair list, launch's household deadlines) and changes no record's time, so a backup's copy carrying the person's change still wins; inside the person's unit it is part of the person's step. Undo opens its unit with `.restoring` and gives no time. Since when a deadline's cycle is known (`Obligation.cycleKnownAt`, read as `cycleKnownSince`, what the catch-up reminder counts from) is kept by the unit too, beside the change times (`CycleTimes`, [Services/Persistence/CycleTimes.swift](ios/DosarCuSina/Services/Persistence/CycleTimes.swift)): a deadline a step makes, or whose due day, reminders' leads, travel margin or status a step changes, gets the step's time, whoever's step it is, the app's included; nothing else moves it (a note, a cost, the reminder time, a snooze). Never read `updatedAt` for when a cycle became known. A built-in category counts only the person's choices (order, shown on the binder, lock) as a change, and one the catalog installs starts at `ChangeTime.unknown`. A backup's writer (`performPrivate`) keeps the times the backup carries and gives none to what it changes itself. A context one background task made for itself and no one else touches (a backup being written) saves through `UnitOfWork.performPrivate(in:)`: once, everything or nothing. An action the person can take back opens its unit with `UnitOfWork.performUndoable(in:)` and returns the `UndoReceipt`; there is no other undo, and an action that can't be undone returns no receipt. A new stored property goes into its model's `storedProperties` list too (`UndoReceiptTests` fails otherwise). Launch saves through it too: `LaunchData` ([App/LaunchData.swift](ios/DosarCuSina/App/LaunchData.swift)) installs the built-ins, refreshes the repair list and works out the household's own deadlines, each step its own app-made unit; a step that fails is logged with `PersistenceLog` ([Services/Persistence/PersistenceLog.swift](ios/DosarCuSina/Services/Persistence/PersistenceLog.swift): the step and the kind of error, never a value) and the next still runs. Never drop such a failure with `try?` (the `silent-action-failure` check covers actions, the unit, the category store's changes, the repair list and `HouseholdRules`). Show save failures with `SaveFailure.message(for:formKept:)`, never the system's error text.

`SideEffectsCoordinator` ([Services/SideEffects/SideEffectsCoordinator.swift](ios/DosarCuSina/Services/SideEffects/SideEffectsCoordinator.swift)) is the **only** path to notifications, the app badge, the widget snapshot and Spotlight (through its indexer hook). Spotlight has one indexer, `SpotlightIndexer` ([Services/SideEffects/SpotlightIndexer.swift](ios/DosarCuSina/Services/SideEffects/SpotlightIndexer.swift)), registered by `shared(for:)`; what it may show is decided once in `SpotlightCatalog` with `SearchPrivacy.mayShowOutside` and `outsideText` ([SpotlightCatalog.swift](ios/DosarCuSina/Services/SideEffects/SpotlightCatalog.swift)). A new kind of result is a new entry there, never a second indexer. Actions save; the coordinator reacts to the save, and to the phone's time moving (midnight, a new time zone, the clock set: `SideEffectsCoordinator.timeChanges`), reading the app's calendar as each pass starts, so it counts days where the phone is then. Never schedule a notification, reload a widget or index anything from a view or an action. Notification permission is asked only with `askForPermission()`, after the in-app explanation or from Settings; it asks whenever the person hasn't decided, whatever there is to remind about (`PermissionPrompt.personAsked`; a pass after a save asks only when something reminds, `inContext`), and returns with the person’s answer, so a screen reads the permission again then (`ReminderPermission` also reads it whenever the app becomes active), never after a pause.

Settings' „Notificări” (`AppPreferences.notificationsOn`, this device's choice, kept once in the App Group's defaults by `NotificationSwitch` because the share extension reads it too) is read once per pass by the coordinator: off, it plans nothing, removes the pending and shown reminders, clears the badge and withdraws the share's notice. Never read it anywhere else in the app; the share extension reads it only through `InboxNotice.announce`.

**One named exception:** the share's notice ("Am primit 2 acte"), in [ios/Shared/InboxNotice.swift](ios/Shared/InboxNotice.swift). The share extension runs while the app doesn't, so it posts that one notice itself (`InboxNotice.announce`), only when notifications are already allowed, never asking; the coordinator withdraws it on every pass (`InboxNotice.follow`) once nothing it announced still waits, and the inbox tells it when that changes (`ShareInbox.didChangeNotification`). It is the only file the architecture check lets reach the notification center outside the coordinator. Never add a second one: anything else the extension needs to say goes through the inbox for the app to act on.

Every "done" or "amână" from outside the app (reminder buttons, the widget's *Gata*, Siri and Shortcuts) goes through `IntentEngine.perform` ([Intents/IntentEngine.swift](ios/DosarCuSina/Intents/IntentEngine.swift)), with the cycle the person saw; never call `ObligationActions` from a notification, widget or intent directly. Get the coordinator with `SideEffectsCoordinator.shared(for:)`, never a second instance. Anything that carries obligations out of the app (reminders, the badge, widgets, intents, Spotlight) reads `ObligationSnapshot.fetchForOutside`, which leaves examples out.

## Secret fields

A field of type `secret` (an electronic identity card's PIN codes) and a secret row under Date importante (`CustomFact.isSecret`, an alarm or Wi-Fi code) follow one set of rules, in [Services/Security/SecretFields.swift](ios/DosarCuSina/Services/Security/SecretFields.swift):

- `AssetActions` seals every secret with `SecretSealer` before saving (`sealing`, `sealingFacts`); the database holds only sealed text. The keys are `SecretKeyring`'s: each device seals with its own key, kept on that device only and never removed, and adds a synced copy to iCloud Keychain under an account of its own, as soon as the binder opens to sync (`SecretKeySharing`, started by `PersistenceController`) and again whenever a code is sealed or opened; every synced copy is kept only while the device is unlocked. Opening tries every key of the person's devices. Never move or delete a device's own key, and never put a key in the binder, a backup or iCloud's database.
- Showing or copying one goes through `SecretReveal`, which asks `BiometricVaultManager.authenticateForReveal` every time and never changes the session. The screens use `DSSecretValueRow` to show and `DSSecretField` to type.
- Anything that carries values out of the binder (search, widgets, notifications, archives, logs) leaves secrets out: use `FieldDefinition.isIndexable`, `SecretFields.stripping` and `SecretFields.strippingFacts`. A sealed value is recognised by its own form, whatever the template says; `FieldFormatter.display` shows it only as a mask.
- An import never brings a secret and keeps the phone's own for the same records, in both modes (`keepingLocalSecrets`, `keepingLocalSecretFacts`).
- Never offer a secret field for a bank card, and never write a real-looking code in tests or examples (use `0000`).
- A bank card keeps its last four digits and never its number, security code or PIN. Any text the binder keeps or shows outside goes through `PaymentCardNumbers`; never add a field, a log line or an index entry that could hold a card number. The rule itself leaves codes whole (digits glued to letters, IBANs that pass their check or carry on an IBAN's groups, and a value whose field type tells it apart, `PaymentCardNumbers.keepsWhole`: an IBAN, a microchip); the same digits as a section's own value kept that way stay whole in all of that section's words, its notes, rows, visits, deadlines and documents' text, where it is stored, in search and in Spotlight alike (`PaymentCardNumbers.KeptWhole`, made only from a value and its field's type: the `kept-whole-without-its-type` check); a new kind of code that must stay whole is taught there, never by skipping the rule for one caller. The text rule itself is in [ios/Shared/CardNumberRule.swift](ios/Shared/CardNumberRule.swift) (with `IBAN`, `RomanianText` and `TextPattern` beside it), so the share extension masks a shared file's name with it (`InboxItem.originalName`); what fields say about values stays in the app's [PaymentCardNumbers.swift](ios/DosarCuSina/Services/Security/PaymentCardNumbers.swift). What is kept is masked in one place: `UnitOfWork` runs `FreeText.mask` on every record it saves ([Services/Persistence/FreeText.swift](ios/DosarCuSina/Services/Persistence/FreeText.swift)), so actions never mask on their own. A new stored text or data property goes into its model's `freeText` (words a person typed or a reader read) or `machineText` (ids, keys, hashes, pictures) list (`CardNumbersKeptOutTests` fails otherwise). A secret is masked before it is sealed (`SecretFields.sealing`). Tests use the networks' published test numbers only (`4111 1111 1111 1111`, `5555 5555 5555 4444`).

## iCloud sync

- `PersistenceController` alone decides whether the binder syncs (`SyncState`, settled by `settleSync`, with `choice` the one rule) and is the one place a container is made (`makeContainer(syncs:)`), with the person's private database of `iCloud.com.ar.dosarcusina.app` only. Development builds sync with CloudKit's development environment; Release builds don't until `syncShipsInReleaseBuilds` is true, which is the project's build setting `DOSAR_SYNC_SHIPS_IN_RELEASE_BUILDS` (compiled in as `SYNC_SHIPS_IN_RELEASE_BUILDS_YES`; never a second switch). A test run never syncs; tests use in-memory containers.
- **The iCloud account is an input.** The store always opens first on the phone alone (once, and in a launch in the background too), and opens with iCloud only once `ICloudAccountReader` says the phone is signed into the account the binder synced with before, or its first one (a digest kept on this phone, `SyncMemory`). iCloud's mirroring clears a store's copy on the phone when its account goes or changes, with whatever hadn't gone up, so a store never opens with iCloud for no account (`.noAccount`) or another one (`.otherAccount`, until the person chooses `syncWithThisAccount`, which keeps a backup of the phone's binder first, `KeptCopies`: a file of its own each time, the newest three kept). The account changing (`CKAccountChanged`), the app leaving the screen and the Settings switch settle it again; iCloud not answering keeps what is. Never open a container with iCloud anywhere else.
- **One health, from iCloud's own reports.** `NSPersistentCloudKitContainer.eventChangedNotification` is read into `SyncEvent` and `SyncProblem` (quota, not signed in, offline, busy) and one `SyncHealth` (`SyncHealthTracker`), only from the open container's own reports (`SyncEventSources`: a step started before it was asked for, or another mirroring's once its own is known, is a retired container's), shown under the switch by `SyncWording.status` with what to do. A full iCloud stops sync on that phone (`SyncPause.iCloudFull`) until "Încearcă din nou"; a store that can't open with iCloud stays open on the phone (`SyncPause.couldNotStart`): the recovery screen is only for a store that can't open at all.
- **Retiring a container.** Whenever the store opens under another container, the old one is retired (`ContainerRetirement.retire`, the one event): every `ContainerHolder` lets go of it at once (Caută's index, the side effects with Spotlight, `SyncedChanges`, every `UndoReceipt`, which then offers no undo, `UndoError.binderReopened`), and `UnitOfWork` refuses every save through it (`BinderReopened`). A screen that keeps something made from the container keys it by the container (`.task(id:)`, `.id(...)`). Something new that holds a container or a context of its own beyond one step is a `ContainerHolder`. Whether a container syncs is kept on the container itself (`PersistenceController.syncs`), never by its address.
- **What follows the binder starts where the store opens** (`PersistenceController.followEveryContainer`, from the app's `init`): the side effects and `SyncedChanges`, so what arrives while the app runs in the background reaches reminders too. Never start them from a screen.
- **Shipping sync to TestFlight** (the owner's call, once the data layout has settled): 1) in CloudKit Console, deploy the development schema to production (only the owner); 2) in a pull request of its own, set the build setting `DOSAR_SYNC_SHIPS_IN_RELEASE_BUILDS` to `YES` in both of the project's configurations (Debug and Release; `ICloudSyncTests.theSwitchIsOneSetting` fails until they agree), which turns on `PersistenceController.syncShipsInReleaseBuilds` and brings back the app's `remote-notification` background mode in Release builds: iCloud's silent pushes wake the app with another device's changes, and `scripts/background-modes.sh` keeps that mode only in a build that syncs (`PersistenceController.buildSyncs`), so a release build never asks to be woken for a sync it doesn't do (`scripts/bundle-check.sh` checks the release bundle on GitHub); 3) archive with the App Store profile, which carries the iCloud container and production push.
- Once the schema is in production, CloudKit only adds: a new model property must be optional or defaulted, never renamed or retyped, never required; a removed one stays in the schema. Every model stays CloudKit-shaped (`ICloudSyncTests.everyModelIsCloudKitShaped`).
- A change from another device never goes through the unit of work: `SyncedChanges` reads it from the store's history, away from the main thread (every context the app makes signs its own changes, `localAuthor`), and tells `SideEffectsCoordinator` and `SearchIndexStore`. Never run a person's step for it, and never make an undo receipt for it. An action from outside the app checks its cycle against the store as it is now too (`IntentEngine.apply`), so an old reminder never closes a cycle another device closed.
- What the app does by itself must give the same result on every device (stored ids, the same record chosen by the same rule): built-in categories (`TemplateStore.installBuiltIns`), household deadlines (`HouseholdRules.reconcile`), what capture learned (`IssuerLessons.settle`, run after `RecordsMeet` at launch and with every synced change, and inside every import), every `DataRepairs` step.
- **Records that share an id are one record.** The same binder on two devices has the same ids, and iCloud keeps each device's record apart, so it can bring two copies of any record. `RecordsMeet` ([Services/Sync/RecordsMeet.swift](ios/DosarCuSina/Services/Sync/RecordsMeet.swift)) is the one step that joins them, for every model, generically through each property's `StoredProperty.meet`: the copy with the smallest `copyID` stays (never a choice by change time, which a device may not have received yet: two devices deciding at once must delete the same copy), with the newer copy's values and own links (`ArchiveMerge`'s rule), every record that pointed at either copy pointing at it, a list it keeps of its own keeping both copies' records, and a document's pages from the newer copy; then the others go. `copyID` (database version 13, every model) is given by the device that made the copy, in each model's initializer, never in a backup (`DossierV3.stayOnThePhone`) and never part of a record's own state; a copy from before version 13 is named only by the device that made it (the store's history tells which copies iCloud brought), and a group waits until every copy is named, however long: no device ever names another's copy. Who made a change in the history is one rule, `PersistenceController.cameFromAnotherDevice` (no author is this phone's). It runs at launch before the repair list (`LaunchData`) and with every synced change before the built-ins (`SyncedChanges.settle`). A new model gets `copyID` and its `storedProperties` give `meet` for free. Never trap on a repeated key anywhere (the `unique-keys` check refuses `uniqueKeysWithValues`): until copies are joined, everything reads them as they come.
- **The app's own steps that act on what is missing wait for the binder to arrive.** `CloudArrival` ([Services/Sync/CloudArrival.swift](ios/DosarCuSina/Services/Sync/CloudArrival.swift)) says whether what iCloud is bringing has all come: not while the first download for the account hasn't finished on this phone (`PersistenceController.binderMayBeArriving`, which tells it; the account the binder synced with is kept before anything comes down, so it never stands for a finished download), nor, in a store that syncs, until this launch's first download has finished (`CloudArrival.awaitFirstDownload`), nor while a setup or a download is under way (the mirroring's `SyncEvent`s, which `PersistenceController.record` hands it; never a listener of its own). A container the controller doesn't run is always whole. When it becomes whole it posts `CloudArrival.didBecomeWhole`, and `SyncedChanges` settles again. `HouseholdRules.reconcile` removes a declaration for a missing tenancy only then, and never one with a completion or a document; `RecordsMeet` joins only then. A new step that removes or makes something because something else is missing reads it too.
- **A built-in category's definition is the newest catalog's.** A build whose catalog is older than one already in the binder (`builtInVersion`) leaves every built-in as it is, and an older catalog never writes over a newer one; only the person's choices (order, shown on the binder) are theirs to sync.
- **A form saves only what was changed in it.** An edit carries what it started from, and the action lays only what the person changed over what is stored now (`ThreeWay`, through `JSONValue.laying` for a value stored as JSON): `AssetActions.update(…startedFrom:)` with a `SectionEditStart` (the section and document edit sheets), `setCustomFacts(…startedFrom:)`, `ProviderActions.update(…startedFrom:)`, `ObligationActions.setReminders(…startedFrom:)`. A new form that writes several values passes what it opened with; never write back a whole draft over the record.
- Examples never reach iCloud: a binder holding them doesn't sync on that phone, examples are loaded only with `ExampleDataService.loadExamples(from:)` (through `PersistenceController.loadingExamples`, which opens the store without iCloud and waits until the container that synced is gone before anything is written), and an import into a binder that syncs leaves them out. Examples aren't offered while the person's binder may still be coming down on a new device (`binderMayBeArriving`, until the first download for the account finished; `BinderArrivingNotice` on the first run and the empty binder).

## Locks

- Which sections are locked is this device's choice, never household data: `SectionLocks` (beside the store, never in it, never synced), read through `CategoryTemplate.isSensitive` and written only through `CategoryTemplate.setLock` (`TemplateStore.setSensitive`). Never store a lock in a model or send it to iCloud. "Începe din nou" leaves the lock file where it is (`PersistenceController.moveStoreAside`).
- **Whether a section is locked never depends on its category's record being there.** Ask the one answer: `asset.isSensitive(template:)` or `isSensitive(among:)`, `CategoryTemplate.isSensitive(key:template:in:)` for a key, `vault.isLocked(asset, template:)` on a screen. Without the record it reads this device's choice for the key, else the catalog's default, else locked (`SectionLocks.lockedWhileUnknown`). Never `template?.isSensitive ?? false` or `?.isSensitive == true` (the `lock-without-its-category` check). Whether anything of the binder is locked, or which categories are, is `BinderLocks` (`read(in:)`, `anySectionLocked`, `lockedKeys`), the same answer asked for every category a section names, so a section whose category hasn't arrived counts: the app-switcher cover, Face ID before a backup, Settings' row and De verificat read it, never the category records filtered by their lock (`\.isSensitive`, `{ $0.isSensitive }`, the same check).
- **Every route and sheet declares its lock** (`AppRoute.lock`, `ShellSheet.lock`, a `RouteLock`: `.open`, `.section(id)`, `.drawnByItsScreen` for a record's screen that draws its own locked state by the same answer, or `.unknownSection` for a record that names no section that can be found, locked while anything of the binder is), and the shell draws each through `RouteLockGate`. A new route or sheet that shows or writes into a section is `.section(id)`; a flow of its own that writes into one ("Scriu eu") wraps its steps in `SectionIDLockGate`. A document's page is behind every section it belongs to, its own, its deadline's and its record's (`Attachment.sections`, `Attachment.lock(among:)`), never only its own.
- **A sheet of a locked screen lives inside its gate.** A screen's own sheets (`.dsSheet`, `.dsFullScreenCover`) are drawn behind the lock of the screen that presents them (`EnvironmentValues.screenLock`, set by `LockGate` around a section's page), so when the lock comes back while one is up it shows the locked state with *Închide* and saves nothing. A screen that draws its own locked state declares the lock its sheets live behind with `.screenLock(…)` (a deadline's page: `ObligationScreen.sheetLock`); „Am rezolvat” (`completionSheet`) and the note sheet (`historyNoteSheet`) are behind their record's own section wherever they open from. The `sheet-outside-its-lock` check fails a struct that decides a lock itself and presents a sheet without declaring it.
- **What names a locked section from somewhere else shows only that it is locked.** A row for another section (a person's documents, a home's subscriptions, a firm's „Are grijă de”, the lists behind „Vezi tot”) is drawn through `SectionRowGate` by `SectionRowLock`: „Act protejat” or „Secțiune protejată” (`LockedWording`), a lock and nothing else, no name, date, badge or digits, opening its page behind Face ID. So are a person's hero (`HolderHero.nextDocument`), a box's line and a hero's status line for a deadline of a locked section filed under an open one (`BoxStatus.line(isSensitive:isLocked:)`), and Agendă's and a firm's last job (`Provider.lastJobLine(isLocked:)`, `LockedWording.job`). Caută is the one place a locked section's deadlines and visits keep their title (the owner's decision), with nothing else, and opening one asks for Face ID. Never write a locked row's words anywhere else.
- **A lock is read whenever it changes.** A screen that keeps what it read (Urmează's snapshots) reads again on `SectionLocks.didChange`; a body that reads the lock while it draws follows it by itself (`SectionLocks` is observable). Closing a deadline reads the lock as it is now, from the deadline (`Obligation.isSensitive(in:)`, also what `IntentEngine` asks), never from a row read earlier.
- **Closing a locked category's deadline asks for Face ID; snoozing never does** (`DeadlineChange`, in `ios/Shared`, the one rule). From outside the app, `IntentEngine.perform` asks through `BiometricVaultManager.confirmClosing` where the surface can (`OutsideSurface.canAskFaceID`: a reminder of a locked category opens the app for "Am rezolvat", `ReminderActions.protectedCategoryIdentifier`; Siri and Shortcuts continue in the app), and otherwise changes nothing (`.leftForTheApp`, waiting in Urmează); inside it, Urmează asks through `confirmClosing` too. Keep the check at the entry (the engine, the routes), never inside `ObligationActions`.
- Locks fail closed. A lock file that is there and can't be read, or none where an older build moved it aside, means every category is locked, built-ins included, whatever was chosen before or meanwhile (`SectionLocks.needsChoosingAgain`), and Settings' switches wait, until the person keeps the locks in Settings (`TemplateStore.keepLocksAsTheyAre`, after Face ID); then each one can be turned off again with Face ID. Never cache a failed read as no locks, never write over a file that couldn't be read (it is set aside), and never drop a lock's write failure: `set` and `adopt` throw, and a new category's lock is kept before the save that makes it (`UnitOfWork`).
- Turning any lock off asks for Face ID every time, even with the session open: `BiometricVaultManager.confirmLowering` gives a `LockLowering`, and every way of lowering a lock takes one (`CategoryTemplate.setLock`, `AppPreferences.setAppLock`, `TemplateStore.keepLocksAsTheyAre`) or throws `LockLowering.Needed`. Turning a lock on needs none. Never confirm a lowering with `unlock`, which is for opening the session. An import only raises locks (`DossierImporter`).
- `BiometricVaultManager` is the one unlock session for the app lock and the section locks. Its timings (the minute away before the session closes) count on `LockClock`, a clock the phone's settings don't move that keeps counting while it sleeps; never `Date` for a lock's timing. `confirmWholeBinder` asks before a backup and before bringing one in, either way, whenever any lock is on.
- `LockCover.decide` is the one rule for when the app is covered (by the scene's `LockCover.Phase`: always in the background, while inactive except behind the app's own Face ID prompt; whether a section lock is on from `BinderLocks.anySectionLocked`, read only as the app leaves the screen with the session open), and `LockWindowHost` draws the lock and the app-switcher cover in a window above every sheet ([Views/Locks/LockWindow.swift](ios/DosarCuSina/Views/Locks/LockWindow.swift)). Never draw a lock as an overlay of one screen. `LockWindowController` covers at once and hides the window only when the fade out has completed, for the latest uncovering only; as the cover goes up it ends typing in every window of the scene (`endEditing`), so the keyboard, which has a window of its own, never shows above it.

- What search may keep, and what may be shown outside the app in the iPhone's search, is decided in `SearchPrivacy` ([Services/Search/SearchPrivacy.swift](ios/DosarCuSina/Services/Search/SearchPrivacy.swift)). ## Navigation

A debounce, a backoff before a retry (`VisionCaptureRecognizer.retryPause`), or how long something stays, is a named duration beside the code that owns it, saying why. The `guessed-pause` check fails on a sleep or delay with a number in it anywhere in the app (services included), its widgets, the share extension and `ios/Shared`.

## Shaped screens

A shared screen whose parts vary by category is a **shaped screen**: what varies is a declared kind with one description, never a default and never a test of which category it is, and the screen holds no words of its own. Today: the visit form (`VisitKind`, `VisitShape`, `VisitFormWording`), „Am rezolvat” (`CompletionKind`, `CompletionWording`), the deadline form (the category's blueprints, `DeadlineFormWording`), a section page's pockets and its „Adaugă…” menu (`SectionPocket`, `VisitKind.pocketWords`, `PocketWording`; Acte's empty line names the papers capture files into the category, `CaptureKindProfile.papersKept(inCategory:)`), the full lists behind „Vezi tot” (`SectionLists`: each list's empty line is its pocket's, the rest `SectionListWording`), adding a section (the category's definition through `AddSectionForm`, `AddSectionWording`; the name before anything is typed is `TemplateDefinition.sectionName`, never the category's plural), the form for a category of one's own (`CustomCategoryForm`: `CategorySwitches.Counter`'s words, `CustomCategoryWording`), the capture review (`CaptureKindProfile`: its `noun`, with whether a paper is written on or in (`Noun.surface`: „Pe factură scrie”, „În contract scrie”) and the paper itself (`Noun.definite`), and `dayMeaning`, `CaptureReviewWording`; a policy's bonus-malus line only where its deadline keeps who it insures, `BlueprintFacts.policyholder`), the photo kept on request (`KeepPhotoChoice`, by `PhotoOnRequest`) and a record's page in Istoric (`HistoryEntryShape`, the record's kind laid over its category's visits, a completion's by its `CompletionRecord`, `HistoryEntryWording`). A sentence that pairs a pronoun with a paper's noun takes it from the noun's declared gender („O păstrez” for „Chitanța”), never written by hand for one paper.

- **A new shared screen's varying parts are a declared kind**: an enum every category states with no default (the compiler refuses one that forgets), and one description per kind that says every field, its words, what is required and what saving keeps, as `VisitKind` and `VisitShape` do for the visit form and `ObligationKind.completion` (`CompletionShape`) for „Gata” and „Am rezolvat”. Words every kind shares go in one wording type beside it (`VisitFormWording`).
- **It is registered** in the architecture check's list of shaped screens (`shaped_screens`, the `text-in-shaped-screen` check), which refuses a text literal in its files, and **it gets an entry in the copy matrix**: `CopyMatrixTests` writes [docs/COPY_MATRIX.md](docs/COPY_MATRIX.md) from the descriptions, for every built-in and one category of one's own per combination of its switches, and fails when the committed file is out of date (bring it up to date with `TEST_RUNNER_COPY_MATRIX_WRITE=1 ./tests/run_tests.sh` and commit the diff). The same tests keep vehicle words („km”, „kilometraj”, „piese”, „marcă”, „ulei”) in a vehicle's kind, a doctor's and a vet's words (`CopyMatrixTests.careWords`) in health and pets, every save requirement within the form's own fields, no empty checklist or list, every deadline stating its completion and every paper's sentences agreeing with its noun, a new section's name never its category's plural, each completion's Istoric page fitting what it is (a visit's provider only on a job or care, „Cui ai plătit” only where it asks what was paid), Acte's line naming its category's papers, no two sentences on one form opening the same way, a paper's „pe” or „în” from its noun, and the bonus-malus line only for a car's RCA.
- **Reviews walk every category through the matrix**: a change to a kind or a screen is read in the matrix's diff, category by category, not on the one category at hand.

## Design system

Everything visual comes from [Views/DesignSystem/](ios/DosarCuSina/Views/DesignSystem/). One component per job; extend it rather than drawing a look-alike.

- **Tokens:** `DS.Space` (4/8 grid), `DS.Radius` with `DS.Radius.concentric(outer:padding:)`, `DS.Control` (44 pt tap targets and the buttons' label heights), `DS.Motion` springs and `dsAnimation` (Reduce Motion handled), palette and type styles. `DS.Motion`, `dsAnimation` and `DSDelayedProgress` live in [ios/Shared/DSMotion.swift](ios/Shared/DSMotion.swift), `DS.Space`, `DS.Control` and `DS.Radius` in [ios/Shared/DSLayout.swift](ios/Shared/DSLayout.swift), and the full-width buttons and `dsPinnedAction` in [ios/Shared/DSButtons.swift](ios/Shared/DSButtons.swift) and [DSBottomBar.swift](ios/Shared/DSBottomBar.swift), so the widgets and the share extension use them too. What the share sheet's confirmation says, and that it stays until "Gata", is `ShareConfirmation` ([ios/Shared/ShareConfirmation.swift](ios/Shared/ShareConfirmation.swift)).
- **Full-width actions:** `DSPrimaryButton` for the main action, `DSSecondaryButton` for any other (with `role: .destructive` for deletions; a pocket's add button is one, `PocketAddButton`, since a section's page has no one main action); `dsFullWidthButton(prominent:)` with a `DSButtonLabel` for a control that isn't a plain button (a `ShareLink`). A small action beside a row is `DSCompactButton`. A screen's or sheet's main action is pinned to its bottom edge with `.dsPinnedAction { DSPrimaryButton(…) }` (or sits in the toolbar's confirming place), never at the end of scrolling content, so it shows at any sheet height and text size; what goes with it goes in the same bar, `note:` above it (why it can't be pressed yet, why the last save didn't work) and `secondary:` under it ("Fă copia fără parolă", "Anulează vizita"). Never draw a bottom bar by hand (`DSBottomBar` is private to `dsPinnedAction`; the `main-action-in-scroll` and `hand-pinned-action` checks). A save that starts work which takes time returns at once while it is already running (`guard !isSaving`), so two quick taps file once; a sheet opens tall enough for what it must show (a calendar opens at full height).
- **Rows that give way:** `DSAdaptiveStack`, side by side when the pieces fit at their natural width, stacked otherwise. Never `ViewThatFits` or a check of the text size for a row (the `view-that-fits` check). Widgets are the one place left out, on purpose: a Lock Screen line shows one line of text the system lays out itself, and offers a shorter wording only through `ViewThatFits`. How many deadlines each widget family shows, and the room a row and its 44 pt *Gata* take, is declared once in `WidgetLayout` ([ios/Shared/WidgetLayout.swift](ios/Shared/WidgetLayout.swift)), with *Gata*'s look `WidgetDoneLabel`; `WidgetLayoutTests` checks they fit the smallest widget.
- **Checklists and single choices:** `DSCheckRow`, the whole row is the target. A choice field (`DSChoiceField`) is a menu up to `menuLimit` options and a searchable list in a sheet beyond it (`DSChoiceList`, `DSChoiceListSheet`: a country); a screen asking one long choice on its own uses the same list.
- **A check's outcome:** `DSReadinessRow` (ready, worth a look, to fix, not in the binder), its colour from `DSStatus(readiness:)`; the whole row opens or adds.
- **Ratings:** `DSStarRating`, read-only or tappable.
- **Example data:** `DSExampleBadge` marks every example record.
- **A document's first page in a row:** `DSThumbnailWell`, passed to `DSListRow(thumbnail:)`; it holds the symbol in the same place until there is a picture (or when there must not be one).
- **Value rows:** `DSReadOnlyValueRow` for amounts and facts, `DSActionValueRow` for a value with one labelled action (copy, call), `DSSecretValueRow` for a masked code shown or copied after Face ID. Every copy goes through `Clipboard.copy(_:_:)`: `.personal` for anything read off an identity document, a sensitive value or anything from a locked section (this phone only, gone after a minute). Their buttons sit beside the value, or under it when they don't fit (`DSValueWithActions`), and never wrap their label.
- **Status badges:** `DSStatusBadge(urgency:daysRemaining:)` for a due day and `DSStatusBadge(expiry:daysRemaining:)` for an expiry draw the urgency the rule gives them; the design system draws a tone, never decides one.
- **Sheets, alerts and dialogs** hang on one view that stays while they are up: the row or button that opens them, or the section's header in a `List`. Never on a `Section` or a `ForEach`: a modifier there reaches each row (and the header and footer) one by one, so it is presented once for each, and the copies that can't present close the screen under them (the `presentation-on-section` check). The share sheet is `SystemShareSheet` in a `.sheet` of that one view.
- **States and feedback:** `DSEmptyState`, `DSErrorState`, `DSLockedState`, `DSDelayedProgress` (waits before showing), `DSToast.undo` (takes the action's receipt; `offer` adds a small next step beside *Anulează*, such as *Adaugă o notă*, and keeps it 8 seconds), `DSToast.failure`, `dsDiscardGuard` with `DSCancelButton` ("Renunță"; "Anulează" is only the undo toast's), `DSFiledPaperNotice` (a bill or an invoice already in the binder, with "Vezi factura" and, when the match isn't certain, "E altă factură").
- **A page's extra actions:** `DSMoreActionsToolbar` with `DSMoreAction`s, by one rule (`DSMoreActionsLayout`): none shows nothing, one shows as itself with its words ("Mută la…"), two or more share *Mai multe*. Never a *Mai multe* menu of one item drawn by hand.
- **The binder's boxes:** `DSBox`, and `DSAddBox` last, naming under its title what can be added that has no box yet (`BinderLayout.addBoxNames` over `SectionOffers.inOrder`). A category with nothing in it has no box (`BinderLayout.holds`); never an empty box on the grid.
- **Fields:** the `DS…Field` controls under `Fields/`, one per field type (`DSSecretField` for secrets), and a deadline's schedule: `DSRepeatField` (how it repeats) and `DSReminderTimeField` (*Ora amintirii*, one row until opened with `startsCollapsed`; a minute of the day and a picker's moment only through `ReminderClock`). Number and money fields turn text into a value only while the person types; showing a value never changes it.

## Words, numbers and dates

- **The catalogs are written as Xcode's build writes them**, so building in Xcode never changes them: `scripts/catalog-check.py --sync` runs Xcode's own sync, leaves out what only a `#Preview` uses, puts the entries in Xcode's order (Finder's, `localizedStandardCompare` in English: `scripts/xcode-catalog-order.swift`) and ends with no newline; the check fails when a catalog isn't in that form. A development build and a release build must find the same strings: code built only in development (`#if DEBUG`, the gallery) writes its sample words verbatim (`galleryWords`), and the release build's job runs the check too.
- **String Catalog:** [Resources/Localizable.xcstrings](ios/DosarCuSina/Resources/Localizable.xcstrings) (the widgets have their own in `ios/DosarCuSinaWidgets/`, and code in `ios/Shared` uses the `Shared` table, [ios/Shared/Shared.xcstrings](ios/Shared/Shared.xcstrings), which both compile). Romanian is the source language. Every count uses plural variations (*o zi*, *2 zile*, *20 de zile*: a count of one is a word, in the "one" variant); never write `count == 1 ? … : …`. `scripts/plural-check.py` fails the test run for a counted string without them; an integer that isn't a count goes in `scripts/not-counts.txt` with its reason. The catalogs list exactly the text the code uses, as Xcode extracts it: `scripts/catalog-check.py` fails the test run for text missing from its catalog or an entry no code uses, and `--sync` brings them up to date with Xcode's own `xcstringstool` (which target's table goes in which catalog is one map, [scripts/string_catalogs.py](scripts/string_catalogs.py)). Adding text in code means adding it to the catalog in the same commit (Xcode does it when it builds; from the command line, `--sync`). A key the code looks up at run time, which the compiler can't see, is marked `"extractionState" : "manual"` in its catalog so it stays.
- **Distances in time:** `DurationWording.distance` (days, then weeks, months and weeks, years and months; never rounded up), `DurationWording.lead` for a reminder's lead, `WhenWording` for "azi", "în 5 zile", "depășit de 3 zile", `DayCount` and `CalendarCount`, in [ios/Shared/DurationWording.swift](ios/Shared/DurationWording.swift).
- **Units:** `MeasurementUnit` ([Models/Values/MeasurementUnit.swift](ios/DosarCuSina/Models/Values/MeasurementUnit.swift)) for a field's unit, a reading's, a counted deadline's and capture's: compare and store its `key`, show its `label`, write a number with its unit through `MeasurementUnit.written`. Never compare or store a unit's display text; a new unit is a new catalog entry.
- **Counts in a sentence:** a `String(localized:)` or `LocalizedStringResource(…)` with a number in it passes `locale: .dosarDefault` (after `table:`, before `comment:`), or the number is written in the phone's region („1,250”); a `Text` takes the screen's locale, the app's. `scripts/plural-check.py` fails one that doesn't, from what the build found.
- **Reading numbers:** `RomanianNumber.read(_:as:from:)` ([Models/Values/RomanianNumber.swift](ios/DosarCuSina/Models/Values/RomanianNumber.swift)), told the kind (money, count, meter index, kilometres), for every capture reader and every field; `RomanianNumber.format` writes what it reads back; `canonical` reads the machine form of archives and stored JSON; a model's answer, whichever model gave it, through `ModelQuestions.number(_:as:)` over both. Never parse a number another way, and never through `Double`.
- **Counting days:** `Calendar.dosar` ([ios/Shared/DosarCalendar.swift](ios/Shared/DosarCalendar.swift)), the one app calendar, as `Locale.dosarDefault` is the one locale: Gregorian, Romanian (weeks start on Monday), in the phone's time zone, read each time so a move to another time zone is followed, whatever calendar the phone is set to (Buddhist, Japanese, Hebrew…). Every default `calendar:` parameter, every "today" and every day made from a moment use it; `Calendar.dosar(in:)` gives it in a set time zone (`CalendarDay.isoCalendar` is it in UTC, for days alone). Screens get it as the environment's `calendar` from `.dosarLocaleAndCalendar()`, set at each root the app draws (the app, the lock's window, the share sheet). Never `Calendar.current`, `Calendar.autoupdatingCurrent` or `Calendar(identifier:)` in app code (the `app-calendar` check); tests may build the calendars they need.
- **Moving a day by months:** `CalendarDay.adding(months:dayOfMonth:calendar:)` ([ios/Shared/CalendarDay.swift](ios/Shared/CalendarDay.swift)), the one month arithmetic: the same day, or the month's last day when it is shorter (31 January and a month is 28 or 29 February, 29 February and a year is 28 February), and with `dayOfMonth` the day a series keeps (a payment on the 31st is back on 31 March). A month's length is only `CalendarDay.daysInMonth(calendar:)`, from the calendar. Repeating deadlines (`RecurrenceEngine.add`), reminder leads in months (`ReminderLead`), the travel cut-off, a month-day in a year (`MonthDay.day(inYear:)`), a day checked from outside (`CalendarDay(validYear:month:day:)`) and capture's lengths (`printed(addingMonths:)`) all go through it. Never a table of month lengths, a switch over the short months or a leap-year rule of one's own (the `month-length` check).
- **Money and dates:** `Money.formatted` and `formattedCompact` ([Models/Values/Money.swift](ios/DosarCuSina/Models/Values/Money.swift)), which write the leu as Romanian counts it (a whole number through the String Catalog's plural forms, `Money.wholeLei`: „1 leu”, „2 lei”, „20 de lei”; with decimals „1,50 lei”; never „RON”) and another currency by its code, and `Locale.dosarDefault`, the one app locale, Romanian whatever the phone's region ([ios/Shared/DosarLocale.swift](ios/Shared/DosarLocale.swift)). Never `String(format:)`.
- **Machine text:** ISO days and hex digests (a fingerprint) are written by `MachineText` ([ios/Shared/MachineText.swift](ios/Shared/MachineText.swift)): ASCII digits, never localized. So is machine JSON: `MachineText.jsonEncoder()` (`.compact`, for what the app, its widgets and its share extension keep and hand each other) or `jsonEncoder(.readable)` (a `.dosar` archive), both writing a moment in UTC to the second, and `MachineText.jsonDecoder()`, which reads every form earlier versions wrote (fractional seconds, any UTC offset, a day alone). Never a date strategy of one's own (the `json-date-coding` check). The widget snapshot is one type, `WidgetFeed` ([ios/Shared/WidgetFeed.swift](ios/Shared/WidgetFeed.swift)): the app builds it (`WidgetFeed.make`) and writes it (`WidgetSnapshotWriter`), the widget reads it.
- **Writing dates:** `DosarFormat` ([ios/Shared/DosarFormat.swift](ios/Shared/DosarFormat.swift)) for every date the app, widgets, notifications and search write, and `DueWording` ([Services/Attention/DueWording.swift](ios/DosarCuSina/Services/Attention/DueWording.swift)) for "Expiră în 5 zile · 7 noiembrie". A due day is a `CalendarDay` ([ios/Shared/CalendarDay.swift](ios/Shared/CalendarDay.swift)), from capture's first reading to the database (where `StoredDay` keeps it as its ISO text), and is written as one, never turned into a `Date` first; numbers from outside become one with `init?(validYear:month:day:)`: midnight in one time zone is the evening before in another. A moment (`Date`) is written in the time zone of the calendar the days are counted in, always in Gregorian numbers.
- **Values from a newer version:** keep what can't be read raw (`FieldValues` keeps unknown entries, `KeptList` unknown entries of a list stored as JSON, `RecurrenceRule.unreadable` an unknown rule, `FieldDefinition` an unknown type or part), behave as the loudest case (`Consequence(stored:)`, `ObligationKind(stored:)`, `ObligationStatus(stored:)`), never write back a downgraded value. Inside what this build reads, every stored JSON object keeps the keys it doesn't know, at any depth, and the values it reads as something else: a single object is a `KeptObject` (a section's values, a category's behaviour, a deadline's recurrence, a document's framing), a list a `KeptList`, and both write an edit over what was stored by one rule (`JSONValue.laying`: what the edit left as read stays as stored; an object whose `type` changed, or a list entry taken out, keeps nothing of the old). Models read and write them only through their accessors (`values`/`keptValues`, `behavior`/`keptBehavior`, …; the `stored-json-outside-model` check), backups carry the kept form, and an exit's rule (secrets, card numbers) reaches the kept parts with `mappingKept`. A new property stored as JSON is a `KeptObject` or a `KeptList` (`StoredObjectsTests` lists them against the schema).
- Copy follows [docs/COPY_GUIDE.md](docs/COPY_GUIDE.md).

## The placeholder-view contract

Screens know each other only by type name and initializer, such as `SectionScreen(assetID:)`, `ObligationScreen(obligationID:)`, `AddVisitFlow(assetID:)` or `OnboardingFlow(onFinish:)`, and move between each other with `AppRoute`. When two branches build screens in parallel, the branch that needs a screen first adds a placeholder with the agreed name and initializer (a `DSEmptyState`), so both branches build on their own. The branch that builds the real screen replaces the placeholder in place and keeps the name and initializer. Never change a screen's name or initializer without updating every caller in the same commit, and list any placeholder still in place in [docs/HANDOFF.md](docs/HANDOFF.md).

# Craftsmanship details

The standing rule above is the bar. These are the SwiftUI specifics.

## 1. Philosophy
- **Restraint and intentionality:** every element, border and margin needs a reason to exist. Chrome recedes so content leads.
- **Invisible polish:** fluid transitions, forgiving touch targets, instant responses, state that's kept.
- **Respect for the person:** never confuse, startle or overwhelm. No dark patterns, no needless modal interruptions. Respect the system settings: appearance, Reduce Motion, Increase Contrast, Dynamic Type.

## 2. Visual and typographic hierarchy
- **System fonts and the type scale** from the design system's type styles, with primary, secondary and tertiary labels.
- **Real typography:** Romanian quotes („ ”), apostrophes (’), en and em dashes, the ellipsis character (…), ș and ț with a comma below.
- **Concentric geometry:** nested corners follow inner radius = outer radius − padding (`DS.Radius.concentric`). All corners are continuous (`style: .continuous`). No sharp children inside rounded containers.
- **Depth:** soft, layered shadows, hairline separators, semantic materials. No heavy borders.

## 3. Motion and tactility
- **Springs only,** from `DS.Motion` (0.2–0.4 s), through `dsAnimation` so Reduce Motion turns movement into a short fade.
- **Physical transitions:** things grow from where they came from (the binder's boxes zoom open).
- **Feedback:** press states on everything tappable, `sensoryFeedback` for success, failure and selection.
- **No layout shift:** reserve space for content that loads, and hold back progress indicators with `DSDelayedProgress`.

# 4. Security and privacy in a public repository

## 4.1 No secrets, no personal data
- **No credentials in the repository:** no API keys, tokens, passwords, keystores, certificates or provisioning profiles.
- **Bring your own key:** the optional AI keys (one per provider: Google Gemini, OpenAI, Anthropic Claude, an OpenAI-compatible service) are entered by the person in Settings and kept in the iOS Keychain (`kSecClassGenericPassword`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, so they never leave the device). They are sent only in request headers, never in a URL. Developers use the same Settings screen with their own key; there is no build-time key. Never commit a key, even a test one.
- **Placeholder data only** (see "How agents work here", item 8). This covers names, emails, phone numbers, plates, VINs, CNPs, document numbers and addresses.
- **Local first, no central database:** data lives in SwiftData on the device and syncs only with the person's own private iCloud database (see "iCloud sync"). There are no servers of ours, no accounts, no analytics and no telemetry. Don't add any SDK that phones home.
- **Privacy manifests and permissions:** the app, the widgets and the share extension each carry a `PrivacyInfo.xcprivacy` in their own folder (the app's in `Resources/`) that tracks nothing and collects nothing (no account, analytics or server of ours; the binder goes only to the person's own iCloud, and a document only to the AI provider whose key they added, which they chose and we can't see), and that lists every kind of API Apple asks a reason for that the part's code uses (`ReleaseReadinessTests.RequiredReason`: the app's own settings, file dates in its own and the App Group's containers, the lock's clock). Code that starts using another one (disk space, say) declares it there with the reason that says what for; the test names the file and fails until it does, and fails too for one no longer used. Every permission the code can ask for has its words in that target's `INFOPLIST_KEY_…` (`ReleaseReadinessTests.permissions`), short and plain as the copy guide says.

## 4.2 What protects the repository
- The versioned pre-commit hook [.githooks/pre-commit](.githooks/pre-commit) and the pull request workflow [.github/workflows/privacy-check.yml](.github/workflows/privacy-check.yml) run the same script, [scripts/privacy-check.sh](scripts/privacy-check.sh). It blocks private and credential paths, keys and tokens, home-folder paths, real-looking CNPs and card numbers other than the published test numbers it lists.
- The script lists patterns only. Never add a finding, a trace or a real value to it.
- A past commit the card-number rule flags, once the owner has checked that it holds nobody's real number and a later commit fixed it, can be listed in [scripts/privacy-reviewed-commits.txt](scripts/privacy-reviewed-commits.txt): its commit id and a reason only. Only the owner adds to that list.
- Links in documents are relative to the repository. Never write an absolute path from your machine.

# 5. Security findings and the private vault

- `private/` exists **only on the owner's machine**. It holds security findings, internal bug traces and anything else that must never be published. It is ignored by git and blocked by the privacy check. Collaborators don't have it and don't need it.
- **Collaborators and their agents report security problems through GitHub's private vulnerability reporting**, as [SECURITY.md](SECURITY.md) explains. Never in issues, commits, code comments, pull request text, test names or documentation.
- Describe behaviour in public, never weaknesses. A fix's commit message says what now happens ("ask before replacing the household"), not how it could be abused.
- If you are the owner's agent: findings go in `private/VULNERABILITY_REGISTER.md`, crash logs and traces with local paths in `private/INTERNAL_BUGS.md`.

# 6. App Store distribution and feature tiers

To meet the App Store Review Guidelines (2.1 and 3.1.1):
- **Free:** the app is free to download and use, with no paywalls.
- **Complete without a key:** everything works offline and without an AI key: unlimited sections, deadlines and reminders, on-device reading of documents, widgets, backups.
- **Optional AI provider:** a key the person brings (Gemini, OpenAI, Claude or a compatible service) improves reading of a document they choose. The UI never blocks or nags anyone who doesn't add one.

# 7. Commits and workflow

## 7.1 Conventional commits

```text
<type>(<scope>): <short description in the imperative>

[optional body explaining why]

Co-Authored-By: <agent> <noreply@…>   (when an agent wrote it)
```

Types:
- `feat` — a new user-facing feature or screen, e.g. `feat(scanner): add live vision preview`.
- `fix` — a bug fix, e.g. `fix(reminders): ask for permission only after the explanation`.
- `docs` — documentation, e.g. `docs(spec): describe the share inbox`.
- `refactor` — restructuring without changing behaviour.
- `chore` — maintenance, build settings, tooling, templates.
- `test` — adding or modernising tests.

## 7.2 Atomic commits
- **One logical change per commit.** Don't mix a fix with a feature or with unrelated formatting.
- **Every commit builds** (`xcodebuild`) and keeps the tests that cover it passing.
- **Check what you stage** (`git status`, `git diff --cached`) so no temporary files, credentials or private notes slip in.
