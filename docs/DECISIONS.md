# Decisions

A dated log of product and architecture decisions, newest first. Each says what was decided and why. A newer decision can replace an older one: add a new entry that says so, and leave the old one in place.

To propose a change to a decision, open an issue with the **Proposal** template or a draft pull request. The owner decides.

---

## 2026-11-11

### The sealing key is shared as soon as the binder syncs
This replaces, in "iCloud sync to the person's own iCloud", when the synced copy is added and how it is kept.
- **Decided:** a device shares its sealing key as soon as the binder opens to sync, at launch and when sync is turned on (`SecretKeySharing`, started by `PersistenceController` whenever the store opens with iCloud), not only when it next seals or opens a code. It runs off the main thread, one at a time, and adds nothing when the key is already shared; a device that never sealed a code makes no key for it. While the phone is locked it tries again once it is unlocked. Sealing and opening still add the copy too. *Alternatives:* share at every launch whatever sync says (a device that doesn't sync has nothing for other devices to open); make the key at launch on every device (a key for codes that may never exist).
- **Decided:** every synced copy is kept only while the device is unlocked, like each device's own key (`WhenUnlocked`, a class that still syncs). Nothing opens a code while the phone is locked: reminders, widgets, search and backups never carry one. A copy an earlier build kept is moved to that class in place, its value untouched, then read back and put back as it was if it isn't there; one that didn't move stays as it was and is tried again next time. Every device moves every copy it sees, its own and the others', so a device still on an earlier build is covered too. A device's own key is never touched. *Alternatives:* write each copy again under a new name and remove the old one, which leaves another device without the key between the two changes reaching it; move only the device's own copy, which leaves a device that never updates as it was.
- **Decided:** a code from another device says what to do, by what this device can tell. When keys of other devices already reach it (iCloud Keychain works here), the device that wrote the code hasn't shared its key yet: „Codul a fost scris pe alt dispozitiv. Deschide aplicația pe el, cu Parole în iCloud pornit, apoi încearcă din nou aici peste câteva minute.” (`SecretFieldError.notSharedYet`). When none does, either cause is possible and the app can't ask the system whether iCloud Keychain is on: „Codul a fost scris pe alt dispozitiv. Deschide aplicația pe el, apoi încearcă din nou aici peste câteva minute. Dacă tot nu se deschide, pornește Parole în iCloud pe ambele, din Configurări.” (`.unreadable`). *Alternative:* one message for both, which told a person with iCloud Keychain already on to turn it on.

## 2026-11-10

### Section locks stay on each device
This replaces the earlier rule that a section's lock is household data.
- **Decided (owner):** each phone or iPad decides for itself what it keeps behind Face ID; a lock opened on one device can't open sections on another.
- **Decided:** the lock leaves the store. Database version 12 (not released yet, so changed in place) no longer keeps `CategoryTemplate.isSensitive`; it reads and writes `SectionLocks`, a small file beside the store (`<store>.section-locks.json`, readable once the phone was unlocked after it started, so reminders and widgets planned in the background follow it), one per store, which iCloud never carries. It is the one source of truth: `BiometricVaultManager`, `SearchPrivacy`, `LockCover`, Caută, Spotlight, widgets, reminders and the backup screen all read it through `isSensitive`. A change is told to the side effects and to Caută (`SectionLocks.didChange`), changes no record and gives no change time. A category this device hasn't decided on is locked as the catalog says (Acte and Sănătate) or as it was made here; one of one's own made on another device starts open here until it is locked here. *Alternatives:* keep the lock in the record and refuse remote changes to it, which CloudKit can't be told; lock every category arriving from another device, which locks a whole binder on a new iPad.
- **Decided:** the upgrade keeps every lock: before the store changes shape, each category's lock as the store had it becomes this device's choice (the version 11 to 12 stage, now a custom one). Duplicate built-ins no longer join their locks; there is none in the record.
- **Decided:** a backup carries the locks of the device that made it, as that device's settings, and bringing it in, either way, may lock a category on this device but never open one, as before. A restore onto a new phone keeps its locks, and nothing in a backup can open a section. *Alternatives:* carry no lock (a restore onto a new phone would open every category of one's own); apply them only when "Înlocuiește tot" lands on a device with none (a second rule for the same field, and a device always has some, the catalog's).

### Examples keep the binder on the phone (owner)
- **Decided (owner):** while examples are in the binder, that phone doesn't sync, as built (see "iCloud sync to the person's own iCloud").

### iCloud sync to the person's own iCloud
- **Decided (owner):** sync is on by default when the device is signed into iCloud. The binder goes only to the person's own private iCloud database (`iCloud.com.ar.dosarcusina.app`, `ModelConfiguration(cloudKitDatabase: .private(…))`): no account of ours, no server, no shared or public database. A switch in Settings (*Sincronizează cu iCloud*, `AppPreferences.syncsWithICloud`) turns it off; off stops syncing and keeps everything on the phone.
- **Decided (owner):** secret codes sync. The sealing key goes through iCloud Keychain, so a code opens on all the person's devices and stays end-to-end encrypted; showing one still asks Face ID every time (`SecretReveal`). Where iCloud Keychain is off, a code sealed on another device stays sealed, says where it opens, and is never written over.
- **Decided (owner):** sync reaches TestFlight only when the owner says the data layout has settled. Development builds (Debug) sync with CloudKit's development environment; Release builds keep the binder on the phone until one named switch is turned on (`PersistenceController.syncShipsInReleaseBuilds`), after the CloudKit schema is deployed to production. Nobody but the owner deploys the schema.
- **Decided:** the sealing keys are a keyring, not one shared key. Each device keeps its own key where it always was (this device only, `WhenUnlockedThisDeviceOnly`), never removed, as the way back, and adds a synced copy of it to iCloud Keychain under an account named after the key (`AfterFirstUnlock`, synchronizable), read back before it counts (`SecretKeyring`). A code is sealed with the device's own key and opened with whichever of the person's keys opens it (AES-GCM tells a wrong key at once). The sealed format doesn't change. *Alternatives:* move the key into one synced item, which two devices that each had a key would write over, losing every code one of them sealed; a key id inside each sealed code, a format change for what trying the few keys already does.
- **Decided:** examples never reach iCloud. CloudKit syncs whole record types and SwiftData can't put one record of a type in another store, so examples can't live in a local configuration of their own. Instead a binder that holds examples doesn't sync on that phone (`SyncState.waitingForExamples`): the store is looked at without iCloud before it opens to sync, loading examples on a phone that syncs opens the store again without iCloud first (`ExampleDataService.forLoading`), and a backup's examples stay out of a binder that syncs (`DossierImporter.keepsExamples`). Sync starts again once they go, when the app next leaves the screen (so "Anulează" on their removal isn't cut short) or opens. Settings says so. *Alternatives:* sync the examples too, so they show and go on every device; duplicate every model type for a local examples store, with a copy across stores when one is adopted.
- **Decided:** a change from another device is written by the system under the store, so none of the person's own steps run for it: no change time (it carries the other device's), no masking again (done where it was typed), no "Anulează". The store's history tells it apart: every context the app makes signs its changes (`PersistenceController.localAuthor`), and `SyncedChanges` reads the transactions signed otherwise since the last read when the store says one came (`NSPersistentStoreRemoteChange`). It tells `SideEffectsCoordinator` (reminders, badge, widgets, Spotlight) and `SearchIndexStore`, which reads again only what changed. Undo now checks the store as well as its context, so it never takes back what another device changed since. *Alternative:* re-read everything on each remote change, which grows with the binder on every sync.
- **Decided:** what the app does by itself on two devices meets as one: each device installs its own built-in categories, so sync brings a second copy of each, and the one installed first stays everywhere, with the person's newer place and visibility and either copy's lock (`TemplateStore.installBuiltIns`, also run when synced changes arrive); household deadlines keep the copy `HouseholdRules.reconcile` already chooses the same on every device; the repair list's findings have stored ids and its steps are idempotent and pick the same records (the firm kept first, the copy furthest on), so two devices applying one repair agree. Locks stay on each device (see "Section locks stay on each device").
- **Decided:** the backup's merge stays as it is beside sync: a backup brought in with "Adaugă" on a binder that syncs is a change made here, and syncs from there. Within sync, CloudKit merges field by field (each save sends what it changed, the field written last wins), finer than the backup's record-level rule.
- **Decided:** a change to whether the binder syncs opens the store again under a new container (`PersistenceController.applySyncChoice`): the screens keep their place, and the side effects, search and synced changes follow the new container. *Alternative:* apply it only at the next launch, which leaves a switch that doesn't do what it says until then.
- **Left open:** not tried between two real devices: the first sync of a large binder, the time a change takes to arrive, conflicts on the same field, iCloud Keychain bringing a key, a device signed out of iCloud, and whether changes made while sync was off are sent once it is on again (the store keeps its history, which the system's mirroring reads).

### A long backup keeps going in the background
- **Decided:** making a copy, checking one and bringing one in each run as one `BackupRun` that the system keeps going once the person leaves the app or locks the phone (`SystemBackupKeeper`): iOS 26's continued processing (`BGContinuedProcessingTaskRequest`, asked for as the step starts, under an identifier of its own that Info.plist allows as `com.ar.dosarcusina.app.backup.*`, with the `processing` background mode), which shows the step's progress (the run's `Progress`, counted in files) and lets the person stop it; and a background task (`beginBackgroundTask`) from the start until that takes over, and as the fallback where it can't (the Simulator, a busy phone: asked with `.fail`, so the answer comes at once). When the fallback's time runs out first, the step stops cleanly rather than be frozen half-way. *Alternatives:* only the background task, which iOS ends after about half a minute, too short for a large binder; a `BGProcessingTask`, which iOS runs when it likes (often at night, on power), not when the person asked.
- **Decided:** a step stopped from the system's progress, or ended by the system, stops at its next file and leaves nothing half-done: an export removes its unfinished file, an import writes nothing (its save is still one unit of work, everything or nothing, and runs to its end once it opens). The screen says so in plain words (`BackupStopped`). *Alternative:* resume a stopped export where it stopped, which needs a half-written file kept on disk.
- **Decided:** the binder's documents are closed to a locked phone (`DocumentFileProtection`, unchanged), so the steps that read or write them wait at their next file while the phone is locked and go on once it is unlocked (`BackupRun.checkpoint`): an export between sections and documents, an import before its unit opens. An import whose unit failed because the phone locked while it ran runs it again once unlocked, up to twice (`BackupRun.writing`), since the unit took everything back. Reading the backup's own file goes on while locked. A file a running backup works on (the copy being written, the working copy of one being read, its documents' files on their way in) is open to a locked phone only while it is open (`completeUnlessOpen`, `BackupFileProtection.working`); a finished backup and a copy waiting for the person are closed to a locked phone again (`complete`, `BackupFileProtection.finished`), as before, set before the file is handed out. *Alternatives:* lower the binder's own protection while a backup runs, which weakens finished files; keep `complete` on the files being worked on, which stops the work about ten seconds after the phone locks with an error the person can't act on.
- **Left open:** the app shows its own progress as before (the working state), not the fraction; the system's progress shows it once the person leaves. Continued processing can't run in the Simulator, so the system's side (its progress, its stop button, the lock) is pinned by tests through a recording keeper and is not seen on a phone yet.

### A deadline's reminders keep what a newer build wrote
This closes what "What a newer version wrote inside a stored object is kept" left for a deadline's own reminders.
- **Decided:** database version 12 adds one optional value to a deadline, `Obligation.remindersData`: its reminder profile's JSON as a newer build wrote it, kept only while it holds something this build doesn't read (a key it doesn't know, a value it reads as another, such as an unknown consequence). The columns stay what this build reads and remain the one place reminders, urgency and the cycle read; the JSON follows them by the stored-object rule (`KeptObject`, `JSONValue.laying`) on every write through `reminders` or `keptReminders`, and goes once nothing more is left in it. A backup carries the profile as stored both ways (`DossierV3.Obligation.reminders` is a `KeptObject`; the `.dosar` format is the same JSON). Words inside it are masked like a recurrence's (`FreeText.json`), and the `stored-json-outside-model` check covers it. Existing deadlines have nothing more to keep; the same version also takes the section locks out of the store, so its stage is a custom one (see "Section locks stay on each device"). *Alternatives:* store the whole profile as JSON and drop the columns, which moves every reader and the fetches that filter on them for a case only a newer build's backup brings; a column per future key, which can't be known.

### Two copies of a firm meet by one rule
- **Decided:** wherever two copies of one firm meet, the repair list joining a firm kept twice and a backup brought in with "Adaugă" whose copy of a firm meets the phone's, one rule decides what the firm keeps (`FirmCopies`): the details the copy that stays has stand (for a backup, the newer copy, by `ArchiveMerge`), each detail it lacks (phone, email, address, notes, rating, "would call again", CUI) comes from the other, and its trades and the sections it works on are both copies'. A firm's details are facts about a real firm, so an empty one means "not known here", never "removed". So a detail the join filled in is never lost when another phone's newer copy of the firm, which never had it, comes in, and that copy's change still comes in. *Alternative:* count the join as the person's change (a new change time): it only helps when the other phone's edit is older than the join, and loses that edit whole when it is (the reason "Change times have one writer" keeps repairs as the app's own steps). *Alternative:* accept the loss, which drops a phone number for good when the removed copy never reached the other phone.
- **Decided:** the price, for firms only: a detail cleared on purpose on one phone comes back from a backup of another that still has it, and so does a trade or a section link taken off. Seen and fixed in one tap, against a lost detail nobody notices. Other records keep the whole-record rule: an emptied note, a lifted snooze, a cleared due reading mean something.
- **With iCloud sync in mind:** SwiftData's CloudKit store (`NSPersistentCloudKitContainer`) records which fields each save changed and merges what arrives field by field, the field changed last winning, so a join made on one phone and an edit made on the other both reach every phone; this rule is what a backup does with the same two copies. Two phones that both join the same pair keep the same firm, since the one kept is chosen by when it was made and its id.

### A shared file's name from before masking is written again once
- **Decided:** a waiting item an earlier version wrote keeps the shared file's name whole on disk. The first time the app reads the inbox (`ShareInbox.contents`, what De verificat reads), each manifest whose stored name differs from the name the shared rule masks (`InboxItem.originalName`) is written again with the masked name, its version and the rest unchanged, with complete protection; the next read finds them the same, so it happens once. Only looking (`waitingItems`, for the share extension's notice and the coordinator) changes nothing, and the extension never needs to, since it masks as it writes. *Alternatives:* a one-off launch step that walks the inbox (a second reader of the manifests beside the one the app already runs); bump the manifest's version for the rewrite, which would tell nothing the app reads differently.

### A restore keeps the phone's own secrets, read or not
- **Decided:** what the phone keeps only for itself through "Înlocuiește tot" and "Adaugă" is taken as stored, not as this build reads it: every secret row of a section (`SecretFields.secretFacts`: those this build reads, with any key a newer build wrote inside them, and those it can't read that say they are secret or hold anything sealed) and every sealed value, read or not (`sealedValues`, `FieldValues.addingUnreadable`). They go back in place of an archive's row with the same id (`KeptList.replacingEntries`). None of them is ever exported, so the phone's copy is the only one. *Alternative:* keep only what this build reads, as before, which lost a newer build's secret rows for good on the first restore.

### A day the calendar doesn't have is never rolled over
This closes what "Backups that restore" left open.
- **Decided:** a day kept as written that its month doesn't have ("2026-02-30", "2026-04-31") becomes a moment in one place, `CalendarDay.moment(atMinute:in:)` (`startDate`, `noonDate` and the reminders' `fireDate` go through it), as its month's last day (`onCalendar`), never the next month's first days: it counts, sorts into Urmează and reminds on 28 February. `DosarFormat` writes it with its own numbers ("30 februarie 2026"), so the person sees what was kept. *Alternatives:* show it as the month's last day too, which hides that the stored day is odd; refuse such days, which "Backups that restore" already dropped because it breaks the repair of other calendars' years.
- **Decided:** the repair list's one rule for kept days that can't be (`DayYearsStep`, stored id unchanged, now *Date care nu pot fi*) also lists a day its month doesn't have, in a year that can be, and offers the month's last day, asking first and naming both days. A year that can't be decides first (a Buddhist year offered back, any other only says what to check). *Alternative:* a second step at the end of the list, which would scan every stored day twice and could offer two answers for one day.

### Backups that restore
- **Decided:** export and import read one set of limits, `DosarZipEngine.Limits.standard`: 65 534 files (a plain ZIP's count; 65 535 marks ZIP64, which the reader refuses), 128 MB per file, names up to 1 024 bytes, a compressed file at most 200 times its stored size once past 1 MiB, and a plain ZIP's 4 GB. The 512 MB cap on the whole archive is gone: it guarded memory, and nothing holds the whole archive any more. The writer checks every file before writing it and stores, rather than compresses, a file that would grow past the reader's limit, so whatever export writes, import reads. *Alternatives:* keep a total cap and check it at export too, which tells a large household it can't have a backup at all; raise the cap to what a phone's memory holds, which differs per phone and still fails on the next one down.
- **Decided:** both ways stream, through files. Export (`DossierArchiveWriter`, off the main thread) reads the records once, then the sections' photos and the documents' files in batches of 32 or 64 MB, each on a context of its own from `PersistenceController.context(in:)`, and writes each file to the archive as it goes; the data files and then the manifest, with every checksum, come last. A password seals the stream chunk by chunk (`EncryptingSink`), in the existing format: a chunk is known not to be the last once a byte after it arrives. Import reads the file a piece at a time (`DosarZipEngine.Reader` over `ArchiveFileSource`, or `DecryptingSource` opening only the chunks a read needs, the last one first to check the password), hashing each file as it reads it. Before the person chooses, the documents' files are only checked (`DossierArchiveReader.summary`); on confirming, each is written to a folder of its own beside the working copy and read back mapped, not copied, as its record is written (`DossierV3.ArchiveFiles`), still as one unit of work. The in-memory ways (`exportData`, `importArchive(Data)`, `createArchive`, `unpackArchive`, `encrypt`, `decrypt`) live only in the tests, over the same writer, reader and sealer. The `.dosar` format is unchanged; the manifest now comes last in the ZIP, which the format always allowed. *Alternatives:* save the import in batches, which breaks everything-or-nothing (a failed "Înlocuiește tot" would leave half a household); decrypt to a second temporary file, which needs the archive's size twice on disk.
- **Decided:** a household that breaks a limit is told so before any file is handed out: the half-written file is removed and the message says what was too much and what to do (a document by its title, a section's photo by the section's name, or too many files or bytes in all). The limits are checked as each file is written, not counted beforehand, since a page's size is known only once it is read. *Alternative:* a first pass over every file to add up sizes, which reads the whole binder twice for a case that almost never happens.
- **Decided (replaces "exporting a backup and Înlocuiește tot ask"):** bringing a backup in asks for Face ID or the passcode whenever any lock is on, in both modes, the same way as an export. *Why:* "Adaugă" also writes into locked sections. *Alternative:* ask only when the archive touches a locked category, which needs the archive read and compared first.
- **Decided:** the backup screen marks its work started before asking for Face ID (`BackupFlow.Work.confirming`), so a second tap during the prompt starts nothing. *Alternative:* disable the buttons from the view, which a second path (a file opened from another app) wouldn't share.
- **Decided:** a protected archive may ask for 1 to 1 000 000 password rounds, and chunks of up to 16 MiB; the writer asserts the same ranges. Every protected backup the app has made used 600 000 rounds and 1 MiB chunks. *Alternative:* accept exactly 600 000, which leaves no room for a future step up.
- **Decided:** an import keeps a deadline's status as the archive has it (`ObligationStatus(stored:)` reads an unknown one as active, the loudest), and a category of one's own keeps its tint, hero and pockets raw; the next backup writes them back unchanged.
- **Decided:** a day an archive brings that the Gregorian calendar doesn't have ("2026-02-30") comes in and goes out with its numbers as written, never rolled over into the next month; since days are stored as days (database version 9), nothing on the way in turns it into a moment. `CalendarDay(isoString:)` stays as it was, keeping the numbers. *Why:* older builds on a phone set to the Buddhist calendar wrote days such as "2567-02-29" (2024 in that calendar), in the database and in backups; the repair list reads them as written and offers them back (`DayYearsStep`, which runs after every import), so refusing such a day would make those backups impossible to put back and would lose the day before the repair could see it. *Alternative (tried first, then dropped):* make `CalendarDay(isoString:)` take only real days and refuse an archive that carries another; it broke exactly that repair. *Left open:* a day such as "2026-02-30", in a year that is the Gregorian one, is still shown as 2 March wherever it becomes a moment; a repair step that offers it would be the place.
- **Decided:** an imported document's creation time is clamped to now like every other time an archive brings, and an interval of none moves no day in any unit (`RecurrenceEngine.add`, one guard for days, weeks, months and years).

### A page that shows a card number is treated by what it shows, not by its kind
- **Decided:** one rule says whether a page shows a whole card number: its text as read holds one by the "anywhere" rule, leaving out the digits a reader read into a field whose type keeps them whole (`CaptureCardMask.showsCardNumber`, through `PaymentCardNumbers.containsCardNumber(_:keeping:)` with the mask's own `KeptWhole`), read on a result as `CaptureResult.showsCardNumber`. Every caller asks it: whether a photo is kept only on request (`CaptureResult.photoIsOnRequest`: the kind's own `photoIsOptIn`, or this), what may leave the phone (`PhoneOnlyReading`, in the engine before anything is sent and on the result after), the picture in *De verificat* (`InboxPreviewer`) and whether a page may be a personal document (`IdentitySignals`). So a receipt, a form or a letter with a card number in one piece keeps its photo only when the person asks, is never sent to the AI provider and shows no picture in the inbox, whatever kind it was read as; and a vet's record whose microchip was read into its microchip field keeps its photo, may go to the AI provider when the person asks, and shows its picture. A bank card is as before: its kind decides by itself.
- **Decided:** the fact is decided on the text before it is masked and kept on the result (`CaptureResult.showedCardNumber`, set by `withoutCardNumbers`, carried by `reinterpret`), since the text handed on no longer holds the digits. It stays once set: read again as another kind, a page that showed a card number still did. *Alternative:* look for the mask ("•••• 4821") in the result's text, as `PhoneOnlyReading` did: no stored fact, but a page that itself prints only the last four (a shop's or a wallet's receipt) would then have its photo kept only on request too, and a hand-made result couldn't say what its page showed. So a page that prints only the last four digits is no longer read only on the phone; it shows no more than the binder keeps.
- **Decided:** the visit form's invoice follows the same rule (`VisitDraft.photoOnRequestKind`, `CaptureFiler.Visit.keepsPhoto`): with *Păstrează și poza actului* off, the visit is saved with its values and no document, and the form says "Am citit factura" instead of "Factura e atașată". *Alternative:* keep an invoice's photo always, as an invoice is the visit's proof: it would keep the one photo the rule says not to keep, through the one path that doesn't ask.
- **Decided:** the choice's words follow the kind: a bank card keeps *Poza cardului* and its sentences; any other page says *Poza actului*, *Păstrează și poza actului*, "Poza arată numărul întreg al unui card. O păstrez în dosar, protejată ca restul actelor." when on and "Poza arată numărul întreg al unui card, așa că nu o păstrez. Păstrez ce am citit pe act, cu numărul cardului ascuns." when off (`KeepPhotoChoice(kind:)`). *Alternative:* the bank card's words everywhere: a receipt's choice would promise "banca, tipul cardului, ultimele 4 cifre", which it doesn't keep.
- **Why:** after PR #71 a receipt with a whole card number was no longer read as a bank card, so its photo, which shows the number, was kept by default; and what may leave the phone still judged a card-shaped number by its digits alone, so a vet's record with a microchip that passes the Luhn check never went to the AI provider and had no picture in *De verificat*. Both now follow what the page shows, by the rule capture's text is masked by.

### A card number names a bank card only with the card's cues; a model reads text masked
- **Decided:** a card-shaped number on a page counts for a bank card only beside the card's own cues, as data on the bank card's profile (`CaptureKindProfile.bankCardCues`, a `CardNumberCues`), read the one way by `DocumentClassifier`: its network's name (`PaymentCardNetwork.words`) or a cardholder's caption anywhere on the page; within two lines of the number, a caption only a card prints over its expiry (`IdentityTemplates.cardExpiryCaptions`: "valid thru", "good thru", "expires end" …) or an expiry written as month and two-digit year ("08/28"); or the number printed in a card's grouping (four by four, 4-6-5). With a cue it weighs what the whole number weighed before (5). In one piece with nothing of a card around it, it is a hint (2) counted only when no kind finds a word of its own on the page, so it names a page that shows nothing else (a card photo whose words didn't read) and never beats a vet record's "microcip", "vaccin" or "medic veterinar". *Alternative:* keep the weight and subtract it when a vet's words are present: a patch for one kind, and the next code that starts like a card would need its own. *Alternative:* never count a bare number at all: a card photo that read only its number in one piece would land as "Alt document", whose photo is kept by default. *Alternative:* skip a number printed on a line with another kind's label for a typed value ("Microcip …"): the field's label isn't the field, and the cues already settle the cases found.
- **Decided:** "valabil până la" and "expiră la" still read a card's expiry but are no cue, since a vaccine, an inspection or a policy print them too; an expiry with a four-digit year ("03/2027", a vaccine's sticker) is no cue either. Cards print month and two-digit year. "Valid until" was added to the card's expiry captions.
- **Decided:** the text a language model reads is masked by the rule capture's result goes through, one function for both (`CaptureCardMask`): strictly when the phone takes the page for a bank card (any run of eight digits or more), else by the "anywhere" rule, keeping whole what the phone read for a field whose type tells it apart (a microchip). `SemanticInput.text` is that text, the only text any tier puts in front of a model; the text as read stays beside it (`recognizedText`) only to check that an answer is printed on the page. A bank card's questions still get what they need: its last four digits ("•••• 1111"), network, expiry and bank are left. So Apple's on-device model never reads more of a card than the binder keeps. *Alternative:* mask strictly whenever the page may be a bank card (`PhoneOnlyReading.mayBeOne`, a whole or masked number, "VALID THRU"): a receipt that shows a card number would lose its other long numbers (a tax ID, an invoice's number) for the model. *Alternative:* leave the text whole, since the model runs on the phone and is never logged, and the answer keeps only four digits: privacy by default says the model shouldn't read what nobody needs.
- **Decided:** the AI provider is sent the questions and the page's picture, never the text the phone read (`CloudCaptureExtractor.request`); a page that may be a bank card is never sent at all (`PhoneOnlyReading`). A request that ever carries text takes `SemanticInput.text`.
- **Why:** a vet record with a Romanian microchip (15 digits starting 642, about one in ten passing the Luhn check like a Maestro card) could be read as a bank card, then masked strictly (its microchip lost) with its photo kept only on request; and the on-device model was the one reader handed whole card numbers.

### A section's typed values stay whole in all its words
- **Decided:** what a section's own values keep whole from the card rule (a value whose field type tells it apart and that passes that type's check, `PaymentCardNumbers.keepsWhole`: today a pet's microchip, digits alone) stays whole wherever the same digits sit in that section's words: its notes, rows and other fields, its deadlines, visits, parts and readings, the titles and text of its documents. One carrier, `PaymentCardNumbers.KeptWhole`, made only from a value and its field's type (`KeptWhole(_:fields:)`, `KeptWhole(typed:)`, `KeptWhole(section:template:)`; the `kept-whole-without-its-type` check refuses any other maker), read by the card rule itself (`redact(_:keeping:)`) and given by every place that masks: the save (`FreeText`, through each model's `HoldsFreeText.keptWhole`, read only when something would be masked), the binder's index and the iPhone's search (`SearchIndexBuilder.keptWhole(by:)` into `SearchPrivacy.redacting` and `outsideText`), and capture's door (`CaptureResult.keptWhole`, the values its readers read for a field whose type keeps them whole). So search finds a section by its microchip as it is stored, and Spotlight shows a title with it as the app does. A card number beside it, or the same shape of digits that no field of the section holds, is still masked; on a bank card nothing is kept whole. *Alternative:* keep only the field itself whole and mask the digits everywhere else (PR #62's rule): search showed a microchip field's value masked about one time in ten, since it masks text without the field's type, and masking a copy of digits the same record shows whole in its field protects nothing. *Alternative:* a flag on each search field saying it is a typed value: a second rule for search beside the save's, and a note or a document's text that repeats the microchip would still be masked in one and whole in the other.
- **Decided:** the text kept from a document keeps a microchip whole when the same digits are its section's microchip, checked by the save each time, not by remembering where capture read it. Capture keeps it whole in the text it hands out when a reader read it for the microchip field, so the review and the document filed with its pet show it; filed elsewhere, or with the microchip changed in the review, the save masks it. *Alternative:* capture records the spans it read as typed values, kept for that save: the next save of the document (a new title, an import) would mask them again, or the spans would need storing beside the text, a second source of truth. The protection comes from the field type, never from the digits: a 15-digit Maestro card can have a microchip's digits, and the only way one is kept whole is by being typed or read into a microchip field, where PR #62 already keeps it.
- **Decided:** the card rule reads text alone and moved to `ios/Shared` (`CardNumberRule.swift`, with `IBAN`, which `FieldFormatter` used to hold, `RomanianText` and `TextPattern`), so the share extension masks the name of a shared file as it writes the inbox manifest (`InboxItem.originalName`), and the app masks one an earlier version wrote when it reads it. What fields say about values (`keepsWhole`, `sanitizing`, `KeptWhole`'s makers) stays in the app, beside the fields. *Alternative:* mask the name only when the app reads the inbox: the name would wait whole in the App Group until then. *Alternative:* a smaller copy of the rule in the extension: two rules that drift.
- **Decided:** a microchip field no longer shows "Din numărul cardului păstrez doar ultimele patru cifre." for a microchip that passes its check (`DSTextKind.typeKeptWhole`), since the save keeps it as typed.

### Since when a deadline's cycle is known is its own
- **Decided:** a deadline keeps since when its cycle is known as it now is (`Obligation.cycleKnownAt`, database version 11, optional), and the one catch-up reminder counts from it (`cycleKnownSince`, read by `ObligationSnapshot`), not from its change time. The unit of work keeps it as it saves, beside the change times (`CycleTimes`): a deadline a step makes, or whose due day, reminders' leads, travel margin or status a step changes, gets the step's time, whoever's step it is, the app's included (a repair that gives a passport its travel cut-off, reminders that follow a document's type, the household's own deadlines). Undo keeps it as it keeps the change time (`ChangeTimes.keptTimes`, never part of a record's own state): back as it was while still as the step left it, a newer one stays, and it never stops an undo. A new stage moves version 10 to 11 (lightweight); version 10 is frozen as `claude/new-meter` shipped it. A deadline from before, or one a backup brings, has none and reads as known since its change time, what reminders counted from before. The `change-time-outside-change-times` check covers it.
- **Decided:** a snooze, the reminder time, a note or a cost don't move it. The person already knew the cycle, and a snooze has its own reminder on the day it ends: a fresh anchor would have added a catch-up at the same time. Before, any edit moved the change time, so a note edited after the catch-up came brought it back once more.
- **Decided (for now):** a backup doesn't carry it (`DossierV3.stayOnThePhone`): it is when this phone's reminders count from, and the archive is being reworked on another branch. *Alternative:* carry it in the archive, so a restore on a new phone keeps the moment exactly; a copy restored today reads its change time, which can be older when the app changed its reminders since, so a catch-up can be missed after such a restore.
- *Alternative:* let the app's steps that change a cycle give a change time; a repaired copy would then win over a backup carrying the person's later change, which is what `ChangeOrigin.app` exists to prevent. *Alternative:* work it out from the cycle's start (the last completion) and the last reminders change; nothing kept says when the reminders last changed or when a paused deadline started again.
- **Why:** since app-made steps stopped moving `updatedAt` (`claude/change-times-one-writer`), a repair that changed a deadline's reminders left its catch-up anchored to an older moment, so the reminder that should make up for warnings already passed never came.

### Numbers, numbered fields and codes are rows

A value in parts is read beside the other fields' labels that start the same way, less its own (`CompositeLabels.table(for:)`, `policy(_:)` with the green card's header); `CompositeLabels.invoice` and `vehicleCard` are gone.
- **Decided:** a label written with dots is a row written with its dots ("c.u.i.", "d.1", "b.", "s.r.l."), and the pattern that reads it is built from the rows by one function, `RomanianFieldExtractor.printed`: each dot printed or left out with a space or none after it, words apart by any space. It builds exactly the patterns that were written by hand, so every reading is the same (the capture tests are the contract; new tests pin the talon's fields, the tax ID's wordings and the legal forms, which had none). The `labels-outside-their-table` check now also refuses a label spelled inside a pattern: letters with optional dots between them, words apart by `\s+`, a field's number that starts a line.

- **Why:** the last "Kind profiles" gap: these wordings were a table shared by several kinds or patterns inside the readers, so a new wording meant new code.

### A new counter: „Contor nou”
- **Decided (owner):** a counter reading lower than the last one gains a third answer, *Contor nou*, beside *Corectează citirea veche* and *Lasă citirea veche*: for a replaced gas, electricity or water meter, a meter that went round from 99999 to 00000, or a car whose dashboard was replaced. It starts a new series from that reading: the old meter's readings stay as history, they no longer count for comparisons with the new one, and *Ultimul index* (or the kilometres) shows the new meter's. The question stays as the owner set it ("… Corectez citirea veche?"); the line under it ends „Dacă e un contor nou, cele vechi rămân în istoric.”
- **Decided:** a new counter is stored as a flag on the reading that starts it, `MeasurementLog.startsCounter` (database version 10, false by default, a lightweight stage; version 9 frozen). The readings of a section in one unit, ordered by when they were read (a reading that starts a counter first among those at the same moment), split at each flagged one (`ReadingSeries.split`, the one order the series, the question and the repairs read); a reading belongs to the newest counter started on or before it, so an old invoice filed late belongs to the old one. *Alternative:* a series number on every reading, which every later reading would have to be given and an old reading filed late would have to be told. *Alternative:* a list of counter changes on the section (a unit and a moment, as JSON), which keeps the change when its reading goes, but is merged with the whole section by a backup's "Adaugă" (an older copy of the section, edited for something else, drops the change while the reading arrives) and needs its own kept-JSON handling. *Alternative:* a record of its own, a new model and a new archive file for one fact.
- **Decided:** a counter lives as long as one of its readings does. The one way a reading goes (`HouseholdMutations.deleteReading`, under `removeReading`) hands the flag to the next reading of the same counter; with none left, the change is no longer known, and the next lower reading asks again. A step that replaces the reading that started a counter (the same bill or invoice filed again, corrected) makes the new one start it, without asking (`PlannedReading.continuesCounter`, worked out before anything is taken away). "Corectează citirea veche" on the new counter records the new reading before it takes the higher ones away, so the counter passes to it.
- **Decided:** rates and projections count each counter on its own. `ReadingSeries` cleans each counter as before (the longest run that never goes down); a rate adds up each counter's distance over its own days (`progress`), the days between the old counter's last reading and the new one's first counting for neither, since how far the car went or how much gas was used then isn't known. The value now is the newest counter's last reading. The distance between two moments (since a part was changed, between two jobs) is counted counter by counter (`distance`): what the old one moved after the first, every counter between whole, what the new one moved up to the second. *Alternative:* the new counter alone once it has enough readings, which throws away years of pace on the day the meter changes and leaves projections on the calendar fallback until then. *Alternative:* carry the old counter on as an offset (the new readings plus the old last one), which takes the gap as zero distance and so slows the pace by however long the gap was.
- **Decided:** the repair list reads counter by counter: a new meter's first reading is never offered as a number that lost its digits, and a visit's round reading before a new counter is never taken for the form's estimate because the next reading is lower.
- **Decided:** taken back right away with „Anulează” (the step's receipt, as every reading step), and later from the section's hero: „Contor nou din 5 octombrie 2026. Citirile de dinainte rămân în istoric.” with *Nu e contor nou* (`AssetActions.notANewCounter`, undoable: „Citirile se socotesc din nou împreună.”), which clears the flag and leaves every reading; the lower ones are then set aside, as any reading that breaks the order. *Alternative:* a row per reading with the action on it; the app has no list of readings, and the hero is where the change shows.
- **Decided:** backups carry it as `startsCounter` on a measurement, written only when true; a backup without it (every one written before) imports as one counter. No repair step: nothing in old data says for sure that a meter was changed, so nothing is guessed; the next lower reading asks.
- **Why:** with two answers, a replaced meter asked on every new reading: correcting deleted the old meter's whole history, and keeping the old one left *Ultimul index* on the old meter forever.

### Undo takes back only what its step changed
- **Decided:** "Anulează" checks and puts back only what the step changed, property by property (`UndoableRecord.isStillAsLeft`, `takeBack`). What counts is the record's own state, by the one definition change times use (`ChangeTimes.isOwnState`: its values and its own links, never its change time or a list of the records that point at it). It refuses only when something of that the step changed was changed again since, with the same message as before. A newer change to another property of the same record stays, and so does its change time; a step's change time goes back only while no newer change gave one.
- **Decided:** a list of the records that point at a record (a section's history, a deadline's completions) follows those records: undo takes back only what the step itself added to it or took from it, and keeps what another step added since. On a record the step only linked to (the section a completion went into) a newer addition never stops "Anulează", so completing another deadline of the same section (from the widget, a reminder, Siri) while the toast shows no longer stops it. On a record whose own state the step changed or that it made, something that came to point at it since was built on the step (a second "Gata" on the same deadline, which can leave its values exactly as the first left them; a document filed under the person the step made), and undo refuses rather than strand it. *Alternative:* never refuse for a pointing record (a second completion of the same deadline would be left closing a cycle that undo took back).
- **Decided:** pictures and files (the schema's `.externalStorage` attributes: pages, a document's file and thumbnail, a section's photo, read from the models, not listed a second time) are compared by their SHA-256 and size (`StoredValue.file`, `FileDigest`), never byte by byte, and a receipt holds no picture in memory. What a record still has, the receipt knows only by digest. What a step takes away (a deleted document's pages, everything a deleted section had, a photo it replaced) is kept on disk for that receipt only (`UndoFiles`): one folder per receipt in the app's temporary folder, a file per digest with complete protection, read back only while it still matches its digest, removed when the receipt goes (the toast left, or the step was taken back), and what an earlier run left is removed at launch. A copy that can't be read back makes undo say so ("Nu mai pot anula, pentru că pozele păstrate pentru asta nu mai sunt pe telefon…"); one that can't be written leaves the step without "Anulează", and the step itself still saves.
- **Alternatives:** keep the pictures in memory up to a size and offer no undo past it (deleting a large section would lose "Anulează", which it has today); keep them in memory as before (unbounded while a toast shows); move them aside inside the store instead of copying (SwiftData doesn't expose its own files to move); refuse on any change to a record the step touched, as before (a widget's "Gata" on another deadline stopped the undo); compare inverse lists too but only for growth (still refuses for the widget case).
- **Why:** the receipt compared each record's whole stored state, pictures and the lists of records pointing at it included, so an unrelated save during the toast (another deadline of the same section completed) made "Anulează" refuse; and it held whole pictures in memory while its toast showed.

### What a newer version wrote inside a stored object is kept
- **Decided:** every object the database keeps as JSON keeps what a newer build wrote inside it, at any depth: a section's values, a category's behaviour, a deadline's recurrence and a document's framing through `KeptObject` (the value this build reads, and the JSON it was read from), and inside a list's entries (sections and their fields and choices, deadlines and their reminders, variants, first due rule and facts, parts, rows under Date importante) through `KeptList`, which now keeps the JSON each entry was read from, by its key or id. Both write an edit by one rule, `JSONValue.laying`: from the stored JSON, what this build read of it and the edited value, what the edit left as read stays exactly as stored (a key this build doesn't know, a value it read as something else), and what it changed is written. *Alternative:* a hidden dictionary of unknown keys inside each type, filled by its own decoder and written by its own encoder (what `FieldDefinition` does for five named keys): about fifteen types with hand-written coding, each nested object its own, and a new type silently without it. *Alternative:* merge over the record's stored data in each model setter only, with no carrier; a backup's records hold typed values, so an import or export would still drop what they carry.
- **Decided:** a value inside one of these objects that this build can't read (an unknown consequence, kind of deadline, box, visit kind, a first due rule in an unknown unit) reads as the loudest or as the case that hides nothing, and stays stored as written until the person sets that value here, the rule `Consequence(stored:)` and `ObligationKind(stored:)` already follow for a deadline's own columns. A first due rule "after an interval" in a unit this build doesn't know now asks for the date, as an unknown rule does, instead of counting days. *Alternative:* the nearest unit this build knows, which would put the first deadline at the wrong time.
- **Decided:** two rules say when a part is still the same thing. An object with a `type` that became another type keeps nothing of the old one (a recurrence turned from an interval into a counter loses the interval's keys; a field that became another type, its type's keys). A list's entries pair by their `key` or `id`, else by being unchanged, else by their place when the list kept its length; an entry taken out goes with what it kept. *Alternative:* keep every unknown key whatever changes around it, which would carry a newer build's settings for one kind of rule into another kind.
- **Decided:** what this build only tidies as it reads (a unit's label read as its key, reminder leads put in order) is written back as stored until that value is changed, since writing this build's form would be a downgrade for every value read as a fallback; a repair that means to rewrite stored values does it in place, as `UnitKeysStep` does. *Alternative:* write this build's form for every key it knows.
- **Decided:** the exits' rules reach the kept parts (`KeptObject.mappingKept`, `KeptList.mappingKept`): a kept part with a sealed code in it, or one that says it is secret, never goes into a backup; a card number in a kept part is masked as the record is saved, and a recurrence's and a document framing's JSON are now masked like a category's (`FreeText.json`), since what a newer build wrote there may be words. *Alternative:* leave them out of the exits as machine text; a newer build's note inside a rule could then carry a card number into the binder and its backups.
- **Decided:** reading stays one decode of the type (`KeptObject.value(in:)`, `KeptList.items(in:)`); the JSON is read beside it only when a value is written or carried by a backup. Models read and write these properties only through their accessors (`values`/`keptValues`, `customFacts`/`keptFacts`, `sections`/`keptSections`, `behavior`/`keptBehavior`, `recurrence`/`keptRecurrence`, `framing`/`keptFraming`); a new architecture rule, `stored-json-outside-model`, fails a write to one of them elsewhere, and `StoredObjectsTests` lists every JSON property in the schema. The database's shape and the `.dosar` format don't change: the same JSON, with more of it kept.
- **Why:** a single stored object was read whole and written back from this build's types, so a key a newer build added (a deadline's reminder setting, a category's new behaviour, a page's new framing choice) was dropped the next time this build saved that object, or exported or imported it.

### Every stored day is kept as a day
- **Decided:** database version 9 keeps every property that means a day as the day's ISO text (`StoredDay`, `2026-11-15`): a deadline's due day (`Obligation.dueDayISO`) and the day its snooze ends (`snoozedUntilISO`), the due days a completion closed and moved to (`HistoryEntry.cycleDueDayISO`, `nextDueDayISO`), a document's date and its last valid day (`Attachment.documentDayISO`, `validUntilISO`). Before, they were moments (noon of the day in the phone's time zone, a snooze the start of its day), read back in the phone's current time zone, so on a phone ten or more hours from where a day was written every due day and expiry showed a day off. Code reads and writes them only through the models' `CalendarDay` properties (`dueDay`, `snoozedUntil`, `cycleDueDay`, `nextDueDay`, `documentDay`, `validUntil`); nothing outside the model converts. `setDueDay` and `dueDay(in:)` are gone, and so is the calendar argument of `Obligation`'s initializer. *Alternatives:* year, month and day as three integers (sorts and filters as well, but three properties per day and a form nothing else in the app uses); one integer `yyyyMMdd` (sorts, but a form of its own beside the archive's ISO days); keep moments and read them in a fixed time zone such as Bucharest (still a moment, and wrong the day the app counts in another zone).
- **Decided:** the ISO text sorts as the days do (four-digit years, zero-padded), so fetches sort by it (`Obligation.byDueDay`, lexical) and a `#Predicate` can compare it (`$0.dueDayISO <= cutoff`); the only fetch that sorted by the old moment (`ObligationSnapshot.fetchAll`, which reminders, widgets, Siri and Spotlight read) uses it. A stored text that isn't a day reads as none; a deadline with none is due on the day it was made.
- **Decided:** the moments that stay moments are when something happened, was made, last changed or was made smaller (`occurredAt`, `recordedAt`, `createdAt`, `updatedAt`, `compactedAt`), and `DaysStoredAsDaysTests` lists every one, so a new day stored as a `Date` fails it. A visit's day (`occurredAt`) stays a moment: it is when the visit happened, and readings and change times compare with it.
- **Decided:** the upgrade is one custom stage (`DayMigration`): before the store changes shape it reads each moment as the day it meant and keeps the days in memory by record (its id and a moment it keeps); after, it writes them into their new places and saves once (`UnitOfWork.performPrivate`), with no change times, since the days mean what they meant. The old moments are not kept in version 9. *Alternative:* an intermediate version keeping both forms, filled by a lightweight stage and emptied by the next (two versions and two frozen copies for one move).
- **Decided:** the time zone a moment was written in wasn't stored, so the upgrade reads it in the phone's time zone at the upgrade (`Calendar.dosar`). It is the one it was written in for nearly everyone (a phone in Romania upgrading in Romania), and noon keeps the day for any time zone up to eleven hours away; a snooze's end, stored as the start of its day, is read as the noon after it, so it keeps its day the same way. A day written on a phone twelve or more hours from where it upgrades can still read a day off once, and stays the day it reads from then on. *Alternatives:* Bucharest's time zone (wrong for a phone that lives elsewhere, and the app never assumed Romania for a moment); guessing the zone from the moment's time of day (noon in which zone is ambiguous across a day).
- **Decided:** the `.dosar` format is unchanged: archives already carried these as ISO days, and a snooze's end as a moment (its day's start where it was written), which the importer reads as a day the same way the upgrade does.
- **Decided:** a new repair step, `DayYearsStep` (*Date cu anul greșit*), at the end of the list, finds a day with a year that can't be (more than 200 years ahead, or before 1800) in a section's date fields and in every stored day. Before the app counted in one Gregorian calendar, a phone set to another calendar wrote the days it worked out itself in that calendar's years (2569 on a Buddhist one). A year 543 ahead of one between 1900 and a hundred years ahead is the Buddhist calendar's, whose months and days are the Gregorian ones: it is offered back, asking first and naming both days. Any other year that can't be (a Japanese era's, an Islamic, Hebrew or Persian year, whose months differ) can't be worked back safely, so the finding only says to check the date (`isFixable` false). *Alternatives:* fix years too low by adding 543 as well (an Islamic or Persian year, 1448 or 1405, would become a likely-looking but wrong day); convert from each other calendar (which one, and which Islamic variant, isn't known).

### A model's numbers are read by the one number reader

### Apple's model asks one question per session, within its context

### Change times have one writer, and the app's own steps don't count
This replaces part of "One merge rule for every record" (2026-11-09): a step no longer sets a change time itself.
- **Decided:** `ChangeTimes`, run by the unit of work as it saves, is the only code that writes `updatedAt` (beside the importer, which writes the archive's times, and a model's initializer, which gives the moment it is made until the unit saves it). The hand-written stamps in the actions, the repair steps, `DeadlineReminders`, `TemplateStore` and the models' setters are gone. An action with a clock passes it to the unit (`UnitOfWork.perform(in:now:)`, `performUndoable(in:now:)`, `save(_:now:)`); a unit opened without one takes the first a step inside it gives, else the moment it saves. A step that writes the same values again changes nothing, so it gives no time. The architecture check rejects any other assignment (`change-time-outside-change-times`). *Alternatives:* keep "a step that sets a time itself keeps it" next to the unit's rule, which is the second path that let mixed clocks in (a model's setter writing the wall clock under an action's test clock); stamp in each action and drop the unit's rule, which every new action would have to remember.
- **Decided:** a unit says whose change it saves (`ChangeOrigin`). The person's step (the default) gives new times. The app's own step (`.app`: installing and upgrading the built-in categories, the repair list, the household's own deadlines at launch) changes no record's time; what it makes has the time it was made. Inside the person's unit an app-made step is part of the person's step (a deadline's reminders following an edit). Undo (`.restoring`) gives none, as it puts the old times back. A backup's writer (`performPrivate`) gives none to what it changes itself (`HouseholdRules.reconcile` inside an import), so those records keep the archive's or the phone's time, and the deadline it makes has the time it was made. *Alternatives:* a flag on each record saying who changed it last, which is a schema change and travels in archives for no gain; stamping app-made changes with the unknown time, which would make a record the app touched look older than a copy nobody changed.
- **Decided:** a repair the owner approves is the app's own step too, not the person's. It corrects what an earlier version saved; stamping it would let it outrank a real change the person made on another phone before the repair, and lose that change with "Adaugă". Not stamping loses nothing: the repair list looks again after every import and finds it again. *Alternative:* count the owner's tap as their change, which is safe only when no other phone has a newer edit.
- **Decided:** a built-in category is the app's definition, the same on every phone. Only the person's choices for it (its order, whether it shows on the binder, its lock) count as a change of it, and one the catalog installs (at launch, or an import that adds the built-ins a backup didn't mention) starts at `ChangeTime.unknown`. So an app update no longer makes this phone's built-ins "newer" and drops the order and choices from another phone's backup. *Alternative:* keep stamping built-ins and let the importer always take a backup's order, which would overwrite a newer reorder made here.
- **Decided:** no repair step for built-ins stamped by earlier updates. A stored change time can't tell an update's stamp from the person's own choice made after it; resetting would make a real later choice lose to an older backup, silently. The effect fades on its own: updates no longer stamp, so the next choice on either phone decides. "Înlocuiește tot" was never affected. *Alternative:* reset built-ins whose order, visibility and lock equal the catalog's defaults, which still guesses wrong for a person who changed a choice and changed it back.
- **Decided:** every import has the repair list look again, in the archive service (`importPackage`, `importPackageAway`), not in the screen that started it. Launch's steps and that look log a failure with the persistence log (`PersistenceLog`: the step and the kind of error, never a value) instead of dropping it; the next step still runs. The architecture check's `silent-action-failure` now also covers the category store's changes, the repair list and `HouseholdRules`. *Alternative:* throw the repair list's failure from the import, which would report a backup that came in whole as failed.

### The card rule leaves IBANs and long codes whole
- **Decided:** the "anywhere" rule (`PaymentCardNumbers.cardNumbers(in:)`) first leaves out of each run of digits what belongs to a code, then looks for a card in what is left (`pieces(of:in:outside:)`), as before: digits glued to a letter, before or after them, with nothing between (an IBAN's account in one piece, its first group after the country's letters, a code such as "AB4111…"), since a card number is never printed glued to letters; the groups of an IBAN that passes its own check, in one piece, in groups, in any case, with spaces or dashes (`FieldFormatter.ibanRanges`); and, where no IBAN passes, groups that carry on an IBAN printed in groups (a listed country's capitals and check digits, then groups of four: "RO49 AAAA 1234 …"), so a mistyped IBAN stays whole too. Whatever is left out of a run makes the rest a part of it, which must pass the Luhn check and be printed like a card. A card number beside an IBAN or a code with a space between is still masked ("RO49AAAA1B31007593840000 4111111111111111" keeps the IBAN and masks the card). *Alternatives:* leave out the whole run when any of it is glued to a letter, which also keeps a card printed after an IBAN with one space; treat any two letters and two digits as an IBAN's start, which keeps a card printed after "AB12 " (only countries that issue IBANs count now); try every length for an IBAN of a country not listed, where, by chance, about one start in five has a length that passes and would keep a card after a two-letter word ("cu", "de").
- **Decided:** inside a long number printed all in groups of four, a card is looked for only at its start, or right after a card found there ("4111 1111 1111 1111 0828", two cards in a row): every part of such a number is grouped like a card, so where the card starts has to show. A 20-digit number in five groups (a health card's) is never cut into one. Inside runs printed otherwise, the rules of "A card number printed next to other digits" stay. The forgiving of a misread check digit stays for a whole run of exactly sixteen digits in fours, standing on its own. *Alternative:* the start or the end of the run, which keeps a health card's last sixteen digits a candidate.
- **Decided:** a value whose field type says what it is stays as typed when it passes that type's own check (`PaymentCardNumbers.keepsWhole`, `typesKeptWhole`): an IBAN and a pet's microchip (ISO 11784, 15 digits, which a Romanian chip's 642 starts like a Maestro card). The save reads the section's fields only when something would be masked (`PaymentCardNumbers.sanitizing(_:fields:)`, given by `FreeText` from the section's category), and capture keeps a microchip it read (`CaptureFieldKey.typeKeptWhole`), so the section is still found by it. A card number typed into a microchip field fails its check (sixteen digits) and is masked. *Alternatives:* every typed field with a check (a phone, a VIN, a plate), but a phone's and a VIN's checks also let a card's digits through (up to 15 digits, 17 characters that may all be digits), and plates and VINs carry letters, which the glued rule already covers; no field exemption, which leaves one Romanian microchip in ten masked in its own field.
- **Decided:** an IBAN is checked at its country's length, as the ISO 13616 registry lists them (`FieldFormatter.ibanLengths`, used by `isValidIBAN` and the finder), with two letters and two check digits first. Before, only a Romanian IBAN's length was checked; a country not listed is still checked by its check digits alone in a field.
- **Measured** (20,000 samples per case, a seeded generator, the rule before and after; no real account numbers): a NatWest IBAN in one piece or in groups 10.0% masked → 0%; Lloyds 2.8% → 0%; a Lithuanian (Revolut) IBAN 3.0% → 0%; a French IBAN of a 300xx bank in groups 17.3% → 0%; a German ING IBAN in groups 10.4% → 0%; a Romanian IBAN in groups with the placeholder bank code 39.6% → 0% (and mistyped, 39.6% → 0%); a 20-digit health card number in groups 4.9% → 0%; a code glued to letters 4.0% → 0%; a 20-digit code in fours 7.9% → 3.9%; a 24-digit code in fours 11.7% → 4.1%. Unchanged, as it can't be told from a card by its digits alone: a 16-digit code standing alone, or after a word and a space, 4.0%; a microchip in plain text (a note), 10.0% (0% in its own field). Every published test number in the earlier cases and beside an IBAN is still masked.
- **Decided:** values an earlier build masked wrongly can't be put back (the digits are gone), so there is no repair step; an IBAN masked that way fails its field's check and is typed again.
- **Why:** since every save masks every record's words (`FreeText.mask`), the rule's mistakes became permanent: an IBAN that happened to hold a card-shaped run lost its digits, then failed its own field's check, so the section couldn't be saved until it was typed again, and "Anulează" brought back the masked text.

- **Decided:** a firm keeps its tax ID (`Provider.taxID`, digits only, without RO). `findOrCreate` finds a firm by its CUI first, then by its name when that firm has no other CUI. Two firms with the same CUI are the same firm; the repair list offers to merge them.
- **Decided:** the database is at version 3: the CUI, what a category does (`CategoryTemplate.behaviorData`) and the last day a filed paper is valid as read when it was filed (`Attachment.validUntil`), all optional. Version 2 is frozen in `Models/Schema/Versions/`, with a lightweight stage and a test that opens a version 2 store. A filed policy shows the end it was read with; last year's policy no longer shows next year's date.
- **Decided:** the repair list offers, with the owner's OK: a CASCO policy's facts kept in a car's RCA fields move to CASCO's; a home policy kept without its deadline gets "Adaugă termenul" on the day the policy says it ends.

### One urgency, one way to say how long
- **Decided:** how urgent a deadline is comes from one rule, `UrgencyRule`, read from its reminder profile: it needs the person from the day its first reminder goes out, never earlier than its consequence's window (legal a month, financial 21 days, health 7, comfort 3), and lateness within its grace days is calm. Urmează's *Acum*, the binder's boxes, a section's badges and hero, expiry fields, the deadline page, the widget, the app badge, Siri and reminders take that result and only draw it: red when late past grace, amber when it needs the person (due today included), calm otherwise. A date on a page (an expiry, a warranty's end) is as urgent as the deadline it drives; a date with no deadline only on the day and after. The rule lives in `ios/Shared`, so the widget runs the same code, and the widget snapshot carries each deadline's rule.
- **Decided:** a reminder's lead of a whole number of months (30 days each, a year 365) is calendar months: it fires on the same day of the month, so the reminder reads exactly what its settings say ("Cu 6 luni înainte", "În 6 luni: Pașaport"). Other leads are days. Leads and counts are written with plural forms ("Cu 7 zile înainte"), like every other count; a count of one is a word since "Counts of one are words" ("Cu o lună înainte").
- **Decided:** one duration wording, `DurationWording`, with two styles: how far a day is (calendar-accurate, never rounded up) and a reminder's lead. One short "when": *azi*, *mâine*, *în 5 zile*, *întârziat cu 2 zile* within grace, *depășit de 3 zile* past it. Every counted string has plural variations, and `scripts/plural-check.py` checks that after every build.
- **Why:** six urgency rules and three duration wordings disagreed. An RCA 20 days out was "Acum" in Urmează and calm on the car's page; a cat vaccine 2 days late within grace was calm in the app and red on the widget, whose count ignored grace; a passport's 6-month lead read "6 luni" on its page and "5 luni și 3 săptămâni" in its reminder, because a lead counted in days fell a few days short of six calendar months.
- **Answered (owner):** all three stay as built: the consequence cap, today in amber, month leads on the same day of the month (see "The owner's answers"). A passport is now amber from its travel cut-off instead (see its entry).

### One number reader, the Romanian way
- **Decided (owner):** every number the app reads, from a document or from a field, goes through one reader, `RomanianNumber`, told what the number is: money, a count, a meter index (or another measured value) or kilometres. A comma is the decimal mark and a dot groups thousands ("1.250,50"); a number with both marks takes the last one as the decimal mark ("1,250.50" too). Kilometres and counts are whole, so "45,724 km" and "45.724 km" are both 45724. Money or a meter index with one mark and exactly three digits after it follows the Romanian rule ("3,750" lei is 3,75; "Index nou: 12.345" is 12345) and, from a document, is marked "Verifică". Anything that can't be read one way only ("-", ".", "12-5", "5²", "12 km" as money) is refused with a message in the field, never read as 0 or cut short.
- **Decided:** the app writes numbers, money and dates in one locale, Romanian, whatever the phone's region or number format (`Locale.dosarDefault`, injected once at the root). Archives and stored JSON keep the machine form ("1250.5"), read with `RomanianNumber.canonical`.
- **Why:** five readers disagreed: "45,724" was 45724 to one and 45,724 to another, a gas index "12.345" lost its thousands, "86,420 km" became 420, and "3,750" lei became 3.750 lei. A field that writes in one convention and reads in another turned a car's 45.724 km into 457.

### Counter readings: one way in, and a lower reading asks
- **Decided:** every reading (the edit form, the visit form, "Gata", capture, examples) is recorded by one path, `HouseholdMutations.recordReading` (`AssetActions.recordReading` on its own), with where it came from: read by the person, from a document, or estimated. A document's reading is dated by the document.
- **Decided (owner):** a counter reading lower than one recorded before it asks: "Kilometrajul e mai mic decât ultima dată. Corectez citirea veche?" "Anulează" goes back to the form to fix the number; nothing is saved before an answer.
- **Decided:** an estimate is only a greyed placeholder in the visit form ("Cifra gri e doar o estimare"); it is never stored. The hero value (the kilometres on the section) is always worked out from the readings, and undoing "Gata" or a visit takes back the reading it recorded.
- **Decided:** every rate and projection reads one cleaned series, `ReadingSeries`: the longest run of readings that never goes down, in date order, the earlier ones winning a tie. A reading that breaks the order is skipped and flagged, never a reason to stop projecting.
- **Why:** the visit form saved its rounded-up guess as a real reading; the next real one then looked like a drop, and one drop switched off every kilometre-based projection for good. A second rate calculator had no check at all.

### The lock and backups
- **Decided:** the app lock and the app-switcher cover live in a window of their own, above every window of the app. A sheet, a full-screen flow or an alert left open stays under them. Links, notification taps and opened backups wait until the app is unlocked.
- **Why:** this is how the system's own apps hide their content: nothing drawn later can end up on top, whatever presents it. Closing and reopening sheets instead would lose what the person was typing and would need every screen to take part.
- **Decided:** the app-switcher picture is covered whenever the app lock is on, or a section lock is on and the session is open.

- **Decided:** a backup can have a password. With one, the whole file is encrypted (PBKDF2-HMAC-SHA256 with 600 000 iterations, AES-256-GCM in 1 MiB chunks) and can't be opened without it. The password is at least 8 characters, typed twice, never kept, and the screen says plainly that a forgotten one can't be recovered. Without one, the backup is an ordinary file, as before.
- **Why:** a backup travels: iCloud Drive, e-mail, another phone. A password keeps CNPs and document photos unreadable wherever the file ends up, while people who keep it somewhere safe aren't forced to remember one. The format is open and documented, so Android can read it.
- **Decided:** the sheet before every backup says what the copy contains, the identity documents included, lock or no lock.
- **Why:** with no lock on, nothing else would stop to say so; it costs no extra tap, because the password sheet opens anyway.
- **Decided:** an archive never changes what the app defines. Built-in categories always take the app's definition (fields, field types, reminders, version); an archive brings only their order, visibility and lock. A lock is never made weaker by an import, sections are filed by the same rule as "Mută la…", no timestamp is later than now, and the app puts back any built-in that differs from its own at launch.
- **Why:** the person's records belong to them and travel; what a PIN field is, or whether Acte is locked, belongs to the app and to the person's own choices on this phone.
- **Decided:** restoring with "Înlocuiește tot" keeps the PIN codes this phone already has for the same records, like a merge.
- **Why:** this decision log promises it; a backup never carries codes, so the phone's own are the only ones that can come through a restore.
- **Decided:** a sealed value is recognised by its own form, wherever it sits and whatever its template says. Every exit (search, archives, widgets, notifications, the box line) leaves it out, and every display shows only the mask.
- **Why:** one rule that doesn't depend on each exit remembering, or on a template being what it should be.

- **Decided:** a personal value (read off an identity document, a sensitive field, anything from a locked section) or a code is copied to this phone's clipboard only, and leaves it after a minute.

Sharing the same photo twice files the second one with the same document (it moves there).

Undoing a visit puts a moved invoice back where it was instead of deleting it. Moving a document out of a locked section, or writing captured values into an existing locked section, asks for Face ID or the passcode first; a new section reveals nothing, so it doesn't ask.
- **Why:** three save paths wrote the same document three ways; the visit path silently dropped an invoice that was already in the binder, and moved documents kept links to their old place.
- **Decided:** a capture lives in a `CaptureSession` owned by what presents it. Closing the sheet (swiped down, closed or saved) cancels whatever is still reading, so a request to the AI provider not yet sent is never sent, and lets go of its pages.

In every other case the review asks once for that document, naming the provider ("Trimit poza la Gemini?"), with the provider's terms link; nothing is sent before yes. Bills, policies and contracts still read by themselves.

- **Decided:** who issued a document or did a job is found with one lookup, `ProviderActions.findOrCreate`: the firm already kept under the same name before a new one, for the filer and the visit form alike. Firms don't keep their CUI yet, so it doesn't decide the match today; matching it first needs a new database version. This extends "A corrected kind brings what depends on it" (below).
- **Why:** an RCA policy corrected from a bill kept the bill's fields and couldn't get its expiry.
- **Decided (owner):** examples become the person's. Only the example loader makes examples; nothing real inherits the mark. ### Bills and contracts belong to their subscription
- **Decided:** an ongoing contract is one record, a subscription. The first bill or contract from a provider makes it; later bills and contracts find it by the codes they print (a POD, a CLC or the phone number first, then the contract number, then the client code) and file under it. Without a code, the provider decides only inside one house; two homes with the same provider never merge, and when the house can't be told the person picks. One engine decides, `SubscriptionMatcher`, and the review's place ("Unde îl pun") is the one way to change its answer.
- **Why:** each month's bill made a new, unrelated "Factură ENGIE" deadline, so nothing knew it was the same contract, and the codes that identify it were already on every bill.
- **Decided:** gas, electricity, water and fixed internet or TV live under the home they supply; a mobile plan lives in Abonamente, like a streaming service. "Mută la…" moves any subscription between homes and Abonamente.
- **Why:** these contracts are tied to an address and each home has its own; a phone contract follows the person. Phone contracts are among the most valuable to track for their costly minimum period.
- **Decided:** a bill is logged in its subscription's history with what it came to, sets "Ultima factură" when it is the newest, and moves the subscription's one "Factura de plătit" deadline to its own due date. With "Plătesc prin debit direct" on, no reminder to pay is made. A bill kept without a place sets no reminder: the loose "Factură <furnizor>" deadline is disabled (kept in the code, not called). Loose ones made before stay as they are; nothing is migrated without the person.
- **Why:** the payment reminder belongs to the contract and to the real due date on the paper; a reminder for something the bank pays by itself is noise.
- **Decided:** contracts are their own kind of document ("Contract sau act adițional"). What they say (the provider, the service, the contract number, the start, the minimum period and its end, the monthly price, the phone number) goes on the subscription, and the end of the minimum period becomes "Se termină perioada minimă", a month before and on the day. Its note says, without promising: "De regulă, de la această dată poți renunța fără penalități, anunțând cu cel mult o lună înainte. E cel mai bun moment să ceri o ofertă mai bună." A minimum period that already ended sets no deadline.
- **Why:** under EU rules (the electronic communications code, art. 105) a fixed term that ends continues indefinitely and can be left with at most a month's notice and no penalty; that day is the best moment to renegotiate. "De regulă" because contracts for energy and other services can differ.
- **Decided:** a bill that hasn't come well past when it usually does (one cycle after the last one, plus ten days for a monthly bill and the provider's usual delay) shows as a calm note in Urmează, under "Din timp": "Factura de la ENGIE n-a venit luna asta". Only for utilities and phone plans that had a bill before; never a notification, never on the badge or in widgets; it stops after two missed cycles.
- **Why:** a missing bill often means it went to an old email or the address changed, and late fees follow; but it is never urgent, so it must not sound like an alarm.

### Reading by evidence: the AI provider as a second opinion
- **Decided:** this replaces the rule in "What a cloud provider's answer is worth" (below, kept as it was). Readers are ranked by evidence in one place, `ReadingArbiter`, not by which ran first. The order: the person's own edits in the review (values, the kind, the place, the title and the name); then checked values from any reader (the machine-readable zone's check digits, a CNP, VIN or CUI control digit, a payment code in a known barcode format); then the AI provider; then the phone's patterns and labels; then Apple's on-device model.
- **Decided:** the AI provider reads the whole page as a full second opinion: it names the kind and every field. Its kind replaces the phone's unless the phone's rests on deterministic evidence (a checked zone, a decoded payment barcode, a provider's known format the classifier agrees with). A value it reads that isn't in the text the phone recognised is kept, marked "Verifică" unless it passes its own check or agrees with the phone; a value outside its plausibility window is still dropped.
- **Decided:** what a reader read differently is shown beside the value kept, with "Folosește-l", never applied by itself: "Pe telefon am citit: …", "Pe telefon părea: <kind>", "<provider> a citit: …", "Pe spatele actului scrie: …". One mechanism for all of them. A disagreement between readers marks the field "Verifică" unless a check settles it.
- **Decided:** "Citește mai bine cu <provider>" is offered whenever a provider is set up, whatever the phone read; for identity documents the line naming the provider and linking its terms stays. A new setting, "Citește automat când nu sunt sigur", off by default, has the provider read right after a weak phone reading: an unsure kind, an identity document without its essentials, a value that failed its check or a cross-check, little text, or a kind only a provider's format named.
- **Why:** a confident wrong reading on the phone (an RCA policy taken for a bill) used to hide the button, stop the model from changing the kind, and grade the model's correct answer against the phone's misread text. The more expensive reading the person chose to pay for must always be able to do better; only checks and the person themselves outrank it.

### Number fields change only while the person types
- **Decided:** a number or money field turns text into a value only while the person is typing in it. Showing a stored value never feeds back into it.
- **Why:** the field read its own formatted text back into the value, and a format and a read under different number conventions compounded: a car's 45.724 km became 457 after one edit. Rounding rules or a longer field would only have hidden it.

### A corrected kind brings what depends on it
- **Decided:** when the person changes a document's kind in the review, its deadline, place, title, name and reminder to pay follow the new kind, unless they already chose those themselves. Routing and the blueprint are worked out again from the new kind.
- **Why:** an RCA policy read as a bill and corrected by hand was saved without its expiry deadline: the kind changed, but nothing that depends on it did.

### Bill readers claim only bills
- **Decided:** a provider's known bill format (Digi, ENGIE, E.ON…) names the kind only when the classifier agrees or isn't sure, and providers are matched as whole words.
- **Why:** an RCA policy mentioning a word inside a provider's name was read as a Digi bill. A specialised reader is strong evidence for its own kind, not for every page that happens to share a word.

### Each car policy keeps its own details
- **Decided:** RCA and CASCO each have their own insurer, policy number and claims phone on the vehicle ("Telefon daune RCA", "Telefon daune CASCO"). A policy whose cover can't be told isn't written into either. Built-in catalog version 7.
- **Why:** a CASCO policy filled the RCA fields, so the number to call after an accident was the wrong one.

### Bill lines: only real lines, and the person can fix them
- **Decided:** line items ("Ce s-a făcut") belong only on service invoices, receipts, veterinary records and unknown documents. A line is kept only when it reads like one: short, with letters, and with an amount or a known part. In the review each line can be corrected or removed, a line added, or all removed.
- **Why:** a CASCO policy's terms came through as dozens of "lines", and there was no way to remove them before saving.

### A photo already in the binder moves to where it's added now
- **Decided:** filing a photo that's already kept moves the existing document to the new place, with what was read, instead of refusing or keeping two copies.
- **Why:** "Adaugă poza actului" with a photo added before saved nothing; the person had no way to know why.

### Adding a document for a person, photo first
- **Decided:** adding a document from a household member starts with three choices, the person already chosen: "Fotografiază", "Din poze", "Scriu eu". A photo goes through capture and becomes one of that person's documents whatever its kind. "Scriu eu" is one screen: the type in big rows, a variant only where the type has real ones, a name that comes by itself ("Cazier judiciar – Manole Corina"), the expiry with its reminder said plainly, and "Salvează". There is no separate deadlines step: the reminder comes from the type's profile and can be changed on the deadline page. Both land on the document's page, which asks for the picture when there is none.
- **Why:** the old way asked for a name the type already gave, then a deadlines step, and only then let the person add the picture. The picture is what people have in hand, and every extra step is a place to give up.
- **Decided:** variants are data on the document type (cazier judiciar, fiscal or auto; card de debit or de credit; carte de identitate electronică or fără cip; pașaport simplu electronic or temporar), offered through a condition on the field and its options, never as special cases in screens. A value that no longer fits its type is dropped on save.
- **Why:** one source of truth for what a document can be, which the add flow, the edit sheet, the naming and the PIN rule all read.

### "Mută la…"
- **Decided:** anything filed under something else (a document under a person, a tenancy or a product under a home) can move to another parent of the same kind from its page, through the toolbar menu or the edit sheet; a document can also go to a new person. A document named after its holder offers to take the new holder's name. The move is one save and the toast takes it back.
- **Why:** the only way before was to delete and add it again, losing its deadline, history and pictures.

### Secret fields (PIN codes)
- **Decided:** a new field type, `secret`, for codes such as the two PINs of the electronic identity card. It is sealed before saving with a key kept in the phone's Keychain (this device only), shown masked, and shown or copied only after Face ID or the passcode, every time, even when the section is open. A shown code hides after 30 seconds or when the app leaves the screen; a copied one leaves the clipboard after a minute and isn't shared with other devices. It never reaches search, widgets, notifications, the box status line, logs or `.dosar` archives; the backup screen says so, and a restored or merged backup keeps whatever codes the phone already has.
- **Why:** people forget these codes, and the card is blocked after a few wrong tries. Unlike the rest of an identity document, a PIN is never needed to fill in a form, so it can afford a prompt every time; a code that left the phone in a backup or a search index would defeat the point. A code moved to another phone with the database can't be opened there, and says so.
- **Decided:** the fields are named as the issuing authority names them, "PIN pentru autentificare" (4 digits) and "PIN pentru semnare" (6 digits), and apply only to the electronic identity card.
- **Decided:** a bank card is never offered a PIN field.
- **Why:** bank card terms forbid writing the PIN down; keeping it would put the person in breach of their card contract.

### AI providers: bring your own key, several providers, one contract
- **Decided:** the optional cloud reading is a provider layer, not Gemini wired in. The person picks Google Gemini, OpenAI, Anthropic Claude or any OpenAI-compatible service (OpenRouter, Mistral, LM Studio or Ollama on the home network) and brings their own key, one per provider, kept only in this phone's Keychain and sent only in request headers. Every provider gets the same request (the page and the document kind's fields as a JSON Schema, from the definitions the app reads with) and its answer goes through the same grounding and checks. The default model per provider is defined in one place and can be changed in Settings. Without a key nothing changes.
- **Why:** people already pay for, or trust, different services, and some run a model at home. One contract keeps the checks identical whoever answers, and a new provider is one small adapter, not a second reading path.

### What a cloud provider's answer is worth
- **Decided:** a value from a cloud provider is kept as read only when it appears in the text recognised on the phone or passes its own check (a CNP's control digit, a VIN's check digit, the machine-readable zone's check digits, a date inside its plausibility window). Anything else is a candidate marked "Verifică" and never replaces a checked value. The provider runs only when the person taps "Citește mai bine cu …"; for identity documents the review first says "Poza actului se trimite la <provider>, cu cheia ta." and links to the provider's own data-use terms. The app doesn't summarise those terms: it links to them.
- **Why:** a model reading a glared photo can be confidently wrong, and an identity document's values end up on forms. The phone's own reading and the documents' check digits are the evidence; the model only helps find what they can confirm. Linking avoids claims that may not hold for every person (Google's terms, for example, treat free keys differently in the European Economic Area).

### Plausible dates per document kind
- **Decided:** each kind of document says, as data, when its dates can fall. A birth date is within the last 120 years and not in the future. An issue date is not in the future and not before the birth date. On identity documents an expiry is between 2000 and 15 years from today (outside: dropped), and an issue date more than 15 years ago is kept only with "Verifică" (permanent cards). The same windows decide the century of two-digit years, in the machine-readable zone and on printed cards.
- **Why:** library photos are angled, glared and blurred, and a misread digit made a passport "expire in 1906". A fixed century rule can't tell a 1952 birth from a 2052 expiry; the window for each date can. Checking every tier's dates before they are merged keeps an impossible date from pushing out a possible one.

### Back of the card vs the person's edits
- **Decided:** when the back of an identity card is added after the person corrected a value by hand, their correction stays. Where the checked machine-readable zone disagrees, the field shows what the back says, with a button to use it.
- **Why:** the person is the final authority on their own data, but a checked value they may have mistyped against deserves to be seen.

### Collaboration
- **Decided:** collaborators work on their own branches and open pull requests into `main`, which the owner reviews and approves. Security problems are reported through GitHub's private vulnerability reporting. The privacy check is versioned in the repository and runs both before each commit and on every pull request.
- **Why:** the repository is public and two collaborators with their own AI agents are joining. The knowledge they need has to be in the repository, and the protection against leaks can't depend on one person's local setup.

### Distances read in the unit a person feels
- **Decided:** how far away something is reads as days under three weeks, then weeks, then months and weeks, then years and months. Leftovers are dropped, never rounded up.
- **Why:** "87 de zile" hides that something is under three months away. Rounding up would show more time than there is.

### Identity documents
- **Decided:** everything read from an identity document (CNP, series and number, birth date and so on) is shown and can be copied. The section's Face ID lock is the protection. It never appears in search, widgets or notifications.
- **Why:** people need these values to fill in forms; hiding them behind extra taps would defeat the binder. The lock protects the section; the places that show content without the lock never get it.
- **Decided:** documents are named "<document> – <Surname Given names>" and filed under the household member they belong to.
- **Why:** one person usually keeps the papers for the whole household.
- **Decided:** known Romanian documents (the new and the old identity card, the passport, the EU driving licence) are read with per-document templates and cross-checks. The person is asked only about doubtful values.
- **Why:** these layouts are fixed and well known, so they can be read reliably; asking about every field would make capture slower than typing.

### Widgets and examples
- **Decided:** widgets never show example data, and examples never notify.
- **Why:** examples are for exploring. A reminder or a widget about a made-up car would be confusing and would erode trust in real reminders.

### Choice values
- **Decided:** choice values are stored as stable keys, not as display text.
- **Why:** display text changes with wording and language; keys keep stored data, archives and rules stable.

### Face ID
- **Decided:** the app lock and the section locks are independent. A failed unlock never ejects the person. The device passcode is the fallback.
- **Why:** people protect different things in different ways. Being thrown out of the app after a failed Face ID is startling and loses their place.

### The share sheet is the main door
- **Decided:** onboarding includes a real practice share and shows how to move the app to the front of the share sheet.
- **Why:** most documents already arrive in Mail or WhatsApp, and many people don't know apps can hand things to each other, or can't find the app at the end of the share row.

### Integrations
- **Decided:** the app works fully without Calendar, Reminders or Contacts, which are optional one-tap extras. Permissions are asked in context. Notification permission is asked only after an in-app explanation or from Settings.
- **Why:** a permission prompt with no context gets refused, and a refused notification permission is hard to undo. Nothing essential should depend on a permission.

### Structure
- **Decided:** four tabs (Dosar, Urmează, Adaugă, Caută). The binder is a grid of boxes, each with one status line. A section shows fixed pockets in one global order. Agenda is a box.
- **Why:** labelled tabs and one predictable page layout are easy to learn, and one status line per box answers "is everything fine?" at a glance.

### Audience
- **Decided:** the reference user is aged 50–60 and not tech-savvy. No horizontal scrolling, no small pull tabs, labelled tabs, big targets, obvious affordances.
- **Why:** these are the people who keep the household's papers and who struggle most with apps built for power users.

### Follow-up after a lapse
- **Decided:** an optional single reminder the day after something lapsed. On by default for legal and financial items; the person can turn it on or off for any item.
- **Why:** a missed legal or financial deadline gets worse every day, so one nudge is worth it. More than one would nag.

### Reminder profiles
- **Decided:** the lead time follows how hard the renewal is. Rovinietă: 7 days before and on the day. Driving licence: 60 and 30 days. Cat vaccine: 1 day, with grace. Dog rabies vaccine: 10 and 4 days, legal, no grace.
- **Why:** a fixed "30 days before" is too early for a vignette bought in a minute and too late for a passport appointment. Reminding when action is actually needed keeps reminders trusted.

### Capture first
- **Decided:** the phone already has calendar, contacts, photos and notes. The app connects them to real-life events, and the main input is a photo or a document shared from another app.
- **Why:** typing details into forms is the main reason people give up on apps like this. The documents already exist; the app should read them.

### Product centre
- **Decided:** the app is a documents binder (*dosar cu șină*) for rare-but-predictable life admin, not a reminders or to-do app. It opens on the binder, not on a list of deadlines.
- **Why:** the value is having everything about the car, the home or the passport in one place when it's needed. Reminders follow from that, not the other way round.
- **Decided:** a smart maintenance log per component (when, how many km ago, cost, supplier, who did it) for every asset type.
- **Why:** "when did I last change it, and who did it" is the question people actually ask, and it applies to cars, boilers and bikes alike.
- **Decided:** people and providers with star ratings; key facts in one tap; purchase information; readiness checks (for example, the passport before a trip).

### Overhaul
- **Decided:** a full "framework, not patch" overhaul instead of incremental fixes, built in waves by coordinated agents.
- **Why:** the first version had one 90-field model and hand-built screens per category; fixing it piece by piece would have kept that structure. A template engine and single paths fix the cause.
- **Decided:** minimum iOS 26, Swift 6.
- **Why:** the app isn't released yet, so there are no older devices to support, and the newer APIs (on-device model, current SwiftUI and SwiftData) remove a lot of workarounds.

### Android and the archive format
- **Decided:** Android is paused, but `.dosar` export and import stay cross-platform, with a written specification and golden fixtures in `shared/`.
- **Why:** one platform done well first. Keeping the format portable means a future Android version can read the same backups without reshaping anything.

### Categories
- **Decided:** categories are one template engine, and the mainstays (car, home, documents, pets) must feel premium.
- **Why:** one engine means every category gets the same reminders, history, search and archive support; the mainstays are what most people use, so they get purpose-built heroes.

### First run
- **Decided:** the first run is empty, with "Explore with examples". Example data is tagged and removable.
- **Why:** seeding fake data into someone's binder mixes it with theirs. Examples on request let people explore, then start clean.

### Face ID
- **Decided:** Face ID is optional, per section, plus an app lock.
- **Why:** most of the binder (the car, the boiler) needs no lock and should open instantly; identity and health papers do.

### Urmează stays short
- **Decided:** the Urmează list must stay short as data grows (the attention model).
- **Why:** a list that grows with every tracked item becomes noise and stops being read.
